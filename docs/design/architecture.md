## Overview

The system is a persistent workspace for running a team of AI agents across software projects.

**Working with agents:**
- A person works directly with an agent in a shared session, or asks a supervisor to delegate a task to a specialist.
- Each agent has a profile, a working directory, a set of tools it can use, and memory it can propose for the owner to approve.
- Agents read and change files, run commands and tests, consult other agents, and report back to whoever assigned the work.
- For longer jobs, an agent works in rounds toward a stated objective. It stops when it meets a completion condition, reaches a limit or deadline, or someone stops it.

**The service** keeps the work running while the desktop is closed, and records enough progress to recover after a restart.

**The desktop** organizes the work around two questions: what needs my attention, and what is still in motion?
- **Inbox:** questions, approval requests, proposed lessons and pull requests ready for review.
- **Work board:** each task is a thread connecting its plan, agents, sessions, decisions, pull requests and final report.
- **From a thread,** the owner can inspect a diff, answer a question, redirect or stop work, or schedule a follow-up.

**Events and records:** external events wake the responsible agent. The service records model choices, token usage, cost, review rounds and outcomes, so the owner can judge which ways of working produce good results.

There is one owner, working from any of their devices. A shared session is the owner and an agent in the same session.

```
desktop (MyGo) ──┐                    ┌──► model providers (subscription sign-ins)
phone (later) ───┼── REST + SSE ──► pocketd ──► PiG durable harness ──► Durable store (SQLite)
                 │   (proto)          │   └──► work database (SQLite)
                                      └──► execution adapters ──► local git worktree
                                                              └──► Coder workspace (coder ssh → pi-env)
```

## Design

### Repository layout

Three Go modules, joined by a root `go.work`. They sit beside the template's files: `AGENTS.md`, `docs/`, `scripts/`, `test/`, `.github/` and `.memory/`. `service` and `desktop` also carry a `replace` for `proto`, so `go mod tidy` resolves it outside the workspace.

```
proto/                 wire types and the Go client
service/
  cmd/pocketd/         the headless service
  pig/                 the only package that imports PiG
  exec/local/          execution adapter: a git worktree on the service host
  exec/coder/          execution adapter: a Coder workspace
desktop/
  cmd/pocket/          the desktop app, which also builds for the iPad
  internal/state/      the data layer and state, no UI (the iPad builds it as it is)
  internal/app/        the window: views on MyGo and frostui
  internal/config/     settings, and the device token in the keyring
go.work
```

All three build with `CGO_ENABLED=0`. The iPad build is the one exception: Go links for iOS only with cgo and Xcode's clang, on a Mac ([ADR-0040](../adr/0040-build-the-ipad-and-iphone-client-from-the-desktops-code-on-mygos-ios-target.md)).

**`make ci`:**
- keeps the template's checks, which need Node.js 22
- adds `go vet`, `gofmt`, golangci-lint, tests with `CGO_ENABLED=0`, and a cross-platform build, for each module
- adds `go tool mygo vet` for the desktop, which checks MyGo's build lifetimes. The desktop's view tests need Pango and cairo, but no display; CI installs them.
- adds `make portable`: `proto` and the desktop's UI-free packages (`internal/state`, `internal/config`, `internal/github`, `internal/icons`) build for `ios/arm64` with `CGO_ENABLED=0`, and the desktop's iOS app, listed as MyGo's build lists it, leaves out MyGo's terminal plugin (`IOS_LEFT_OUT`).

### Protocol

`proto` holds every wire type and the Go client. The service and every client import it. [specs/protocol.md](../specs/protocol.md) is the contract; `service/internal/api` serves it.

- **Commands:** REST calls with JSON bodies.
- **Live updates:** one SSE stream. It opens with a `hello`, at the client's `Last-Event-ID` or at the newest event, so a client always has an event to come back from; before a `resync`, at a number that resyncs again. Each entry is followed by its session, with the new `updatedAt` and usage. A session's live state carries the messages that wait for a run.
- **Version:** the client sends the protocol version, and the service checks it. The version is `proto.Version`, 28 now: a client and a service of different versions refuse each other, so neither keeps code for the other's.
- **Sessions:** a session carries the profile it started from and the route that chose its model; a thread's worker also names the specialist's session that started it, `startedBy`, read from the thread that names it its worker in every copy of the session, the list's, the detail's and the events' ([protocol rule 23a](../specs/protocol.md)). The desktop nests the worker under that session.
- **Request ids:** every state-changing request carries one. The service applies each request id once and records its author.
- **Authentication:** one owner, with a token per device (`pocketd device add NAME`).

### Service

`pocketd` runs agents on PiG's `durable/harness`.

**Built (Phase 1):**
- **`service/pig`:** the only package that imports PiG; golangci-lint's depguard rule refuses an import anywhere else. It opens the harness over `durable.sqlite`, registers PiG's coding tools (read, write, edit, bash) and the approval hook, runs every command under bubblewrap ([ADR-0012](../adr/0012-run-tools-without-approval-in-a-sandbox-that-hides-pocketds-files.md)), which, like the file tools, keeps the skills folder and the uploads folder read-only to agents ([ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md)), follows each session with a conversation watch, and converts entries and live state to `proto` types through Pi's JSON wire form. It gives each user entry the submission that placed it, read from the durable store's submission records, and each model the thinking levels PiG reads from its catalog entry. A session's live state lists its queued messages from the conversation's `pi.inbox`. A watch update it fails to read is read again after a second, not at the next commit, and so is a session event `service/internal/api` fails to read.
- **`service/internal/store`:** the work database, `work.sqlite`, with devices, sessions, request ids, approvals, threads and asks, lessons, pull requests and verdicts, plans with their graphs and consults, the notes pocketd owes sessions and the questions put to the owner ([ADR-0048](../adr/0048-put-the-supervisors-and-a-private-agents-questions-to-the-owner-inline-in-code.md)), the search index of every session's entries with each session's cursor ([ADR-0050](../adr/0050-search-every-session-through-an-fts5-index-in-the-work-database.md)), versioned by append-only migrations, and the schedules with when each goes out next ([ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md)), and the gathers with their asks and proposals ([ADR-0033](../adr/0033-gather-proposals-from-the-team-in-read-only-sessions-in-code.md)).
- **`service/internal/approvals`:** the approval rule (`NeedsApproval`: no tool waits, [ADR-0012](../adr/0012-run-tools-without-approval-in-a-sandbox-that-hides-pocketds-files.md)), and the manager that records an approval, waits for the decision and wakes the call; `Questions`, which holds a question call for the owner's answer the same way ([ADR-0048](../adr/0048-put-the-supervisors-and-a-private-agents-questions-to-the-owner-inline-in-code.md)).
- **`service/internal/events`:** the event hub. Its numbers grow across restarts, it keeps 4,096 events for reconnecting clients, and it sends a resync when a client missed more. It gives each stream the seq of its `hello`, and a client whose last event came just before a lost one gets a resync.
- **`service/internal/api`:** the HTTP server of the protocol.
- **`service/internal/auth`:** device tokens. Only their SHA-256 is stored.
- **`service/internal/profiles`:** reads the agents' profiles from the profile folder, `-profiles` (default pi-pocket-team's `~/.config/pi-pocket-team/agents`), and checks every field in code; only `<id>.md` files are profiles ([ADR-0013](../adr/0013-load-agent-profiles-from-the-owners-folder-and-route-models-in-code.md)).
- **`service/internal/router`:** chooses every model and names the rule that chose it: the owner's model, the profile's, or the profile's model under a provider alias (`openai` to `openai-codex`). The session records the rule as its `route`.
- **`service/internal/team`:** the rules of delegation, reports and asks ([ADR-0014](../adr/0014-delegate-in-threads-with-team-tools-in-code.md)): who may delegate to whom, the desk's cap, the limits on tasks, reports and asks, the thread's worktree and branch names, and the texts pocketd writes: the brief, a supervisor's roster, a report and an answer, and the sections of the files a session's instructions hold ([ADR-0043](../adr/0043-load-the-global-and-folder-agents-md-and-the-skills-into-every-session.md)). It also holds the lessons' rules ([ADR-0015](../adr/0015-keep-each-agents-lessons-approved-by-the-owner-in-code.md)): their text, their limits, `team_memory`'s answers and the lessons section of an agent's instructions. And the plans' rules ([ADR-0020](../adr/0020-plan-before-building-with-the-plan-gate-and-consults-in-code.md)): the plan gate (`team.Gate`, `team.PlanGate`), the graph's (`team.CheckGraph`), when a task is done (`team.TaskWorkDone`), the consults' bounds, and the texts of the planning brief, the consult's question and pocketd's notes. And where a session the owner starts on a repository works ([ADR-0027](../adr/0027-start-the-owners-session-on-a-repository-in-a-new-worktree-named-in-code.md)): its checkout (`team.SessionCheckout`) and its worktree (`team.SessionWorktree`).
- **`service/internal/schedule`:** the rules of scheduled messages ([ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md)): pi-pocket's grammar of when one goes out (`schedule.Parse`), wall-clock times in a zone across daylight saving (`schedule.Moment`), the limits (`MinRepeat`, `MaxText`, `MaxPerSession`) and the texts pocketd writes, `[scheduled] <message>` and `team_schedule`'s answers. It carries Go's own zone database.
- **`service/internal/github`:** reads a pull request, its labels and CI at a commit on GitHub with `gh`, through a runner pocketd gives it (`Engine.GH`, in the sandbox), and checks GitHub's answer field by field ([ADR-0016](../adr/0016-link-reported-pull-requests-to-threads-checked-on-github-in-code.md)). It writes one thing: the `ready-for-human` label (`SetLabel`, [ADR-0017](../adr/0017-record-cross-review-verdicts-and-set-ready-for-human-in-code.md)). `team.CheckPull` holds the rules of which pull requests belong to a thread.
- **`service/internal/worktree`:** makes a thread's git worktree next to the repository's checkout, on its own branch from the tip of `origin`'s default branch, fetched in the sandbox first, or from `HEAD`, with the reason in the brief, when the fetch fails ([ADR-0056](../adr/0056-start-a-new-worktrees-branch-from-a-fresh-fetch-of-the-remotes-default-branch.md)), and the one a session the owner starts may work in ([ADR-0027](../adr/0027-start-the-owners-session-on-a-repository-in-a-new-worktree-named-in-code.md)). git runs in the sandbox, through the engine, so a hook or filter of the checkout runs with an agent's rights. It removes a closed thread's worktree, never with force, and only one that holds no work outside its linked pull requests (`worktree.Remove`, [ADR-0054](../adr/0054-remove-a-closed-threads-worktree-in-code-with-no-github-write.md)).
- **`service/internal/terminal`:** the owner's terminals ([ADR-0025](../adr/0025-give-the-owner-a-shell-on-the-service-host-from-the-desktop.md), [protocol rule 56](../specs/protocol.md)), pi-pocket-team's terminal module in Go: login shells of the service user, each in a session of its own on a pseudo-terminal opened with `golang.org/x/sys/unix` (no cgo), outside the agents' sandbox, with pi-pocket-team's allowlist of pocketd's environment. It keeps the last 256 KiB of each shell's output for a long poll that names how much the client has, holds a shell back while its slowest client draws, writes each client's numbered keys once, and ends a shell on `DELETE`, at its exit, 60 seconds after its last poll, 60 minutes after its last input, or at pocketd's stop. A shell is reaped under the lock that signals its process group, so no signal reaches an id the kernel gave to another process, and it holds its place under the cap of 4 until its process is gone. Keys wait for room, 32 KiB at most, as on a full pipe. The output kept is a ring, so a write copies only its own bytes, and a poll from past the end holds back no less output for it. A start's request is recorded with its shell's id before the shell starts, so a retry never runs a second login. The device token is its only gate: the agents' sandbox and `guardedEnv` stay for the agents' tools. Nothing logs a key or the output.
- **`cmd/pocketd`:** the commands `serve`, `device add|list|revoke`, `login PROVIDER`, `models`, `profiles` and `version`. `serve` takes `-desk-cap` (default 12), `-skills` (the skills folder a gather reads and every session lists, default `~/.pi/agent/skills`), `-instructions` (the owner's global `AGENTS.md`, which every session's instructions hold, default `$POCKETD_INSTRUCTIONS`, else `~/.pi/agent/AGENTS.md`; `""` for none, [ADR-0043](../adr/0043-load-the-global-and-folder-agents-md-and-the-skills-into-every-session.md); read-only to agents, [ADR-0045](../adr/0045-make-the-global-instructions-file-read-only-to-agents.md)), and at start sends each report and answer that did not reach its session.

**Intended:**

- **Durable store:** holds conversations, tasks, submissions and the usage ledger.
- **Work database:** a separate SQLite file holding threads, plans, plan tasks, asks, pull requests, review verdicts, lessons, rounds and run records. Rounds and run records are still to come.
- **`service/pig/`:** wraps the harness, PiG's `env`, `ai` and `mcp` packages, and the sign-ins.
- **Usage by day (built, [ADR-0052](../adr/0052-show-each-sessions-context-fill-and-usage-and-sum-the-days-usage-in-code.md), [protocol rule 64](../specs/protocol.md)):** `GET /v1/usage?since=<day>` sums the usage of the sessions' answers by day, in the service's time zone, and by model. It reads the answers from PiG's transcripts (`Engine.UsageEntries`), newest first down to the first before `since`, of every session it keeps or that was updated in the last 92 days: the transcript, not the session's time, says whether a session has an answer since `since`. It keeps the days' sums of each session in memory and reads on after the newest entry it read, so each answer is read once while pocketd runs. Nothing goes to the work database. A cost is spend only from a metered provider, an API key's or the owner's own: `service/pig` sends a subscription's usage, signed in by OAuth, with a cost of 0 (`meteredBy`), in a session's usage, its entries and its live reply too; a report prices the days' sums by the provider of each answer's model, as its sign-in is then.

**Agents and profiles:**
- **Profile fields:** `model`, `role` (supervisor, clerk or agent), `repositories`, `workspace`, `home`, `mcp`, `tools`, `private`, `worker`, `session: standing` with its `compactAt` ([ADR-0026](../adr/0026-keep-the-supervisor-in-one-standing-session-compacted-early-in-code.md)), and `questionMinutes`, a supervisor's or a private profile's ([ADR-0048](../adr/0048-put-the-supervisors-and-a-private-agents-questions-to-the-owner-inline-in-code.md)). The body of the profile is the agent's identity prompt.
- **Applying a profile (built):** a session from a profile gets the routed model, exactly the profile's tools, the profile's identity after pocketd's instructions, and the profile's home as its folder; a private profile works only there. A private profile's identity starts with its own preamble (`team.PrivateIntro`: the owner's personal agent, with no supervisor, team or desk), and its sessions get no roster, no lessons section and no team tool ([ADR-0042](../adr/0042-give-a-private-agent-its-own-preamble-and-no-team-in-its-sessions.md)). The profile folder is read-only to agents, as pocketd's start files are.
- **What a session's instructions hold (built, [ADR-0043](../adr/0043-load-the-global-and-folder-agents-md-and-the-skills-into-every-session.md)):** pocketd's preamble, the owner's global `AGENTS.md` (`-instructions`, `~/.pi/agent/AGENTS.md` by default, read-only to agents, [ADR-0045](../adr/0045-make-the-global-instructions-file-read-only-to-agents.md)), the identity (the team's, a private agent's, or a worker's), a supervisor's roster, the `AGENTS.md` of the session's folder, the skills of the global skills folder (`-skills`) and of the folder's `.pi/skills`, listed by the name and description of each `SKILL.md`'s frontmatter with its path, and the lessons section last (`sessionInstructions`, `team.Instructions`). A cross-review reads nothing of its folder, the change it reviews. pocketd reads them all in one run of its own `pig.ContextHelper` in the sandbox (`Engine.loadContext`), as the agents' own tools would, links followed as the sandbox shows them, each file bounded (64 KiB an `AGENTS.md`, 8 KiB a `SKILL.md`'s head, 100 skills a folder); a file over its bound, not UTF-8, or holding a lessons line, a skill whose frontmatter is wrong, a global `SKILL.md` or a global `AGENTS.md` with another name, and a read the sandbox cannot make are notes (`team.GlobalSection`, `team.FolderSection`, `team.SkillsSection`, `team.UnreadNote`, `profiles.ParseSkillHead`), never a session that fails. It reads them when a session is made and when a standing session starts over, and keeps what it wrote with the session (the PiG document `pocketgo.loaded`), which a standing session's refresh writes again without reading a file; a session made before keeps its instructions, a standing one until its next Start Over.
- **MCP and skills:** the service connects these to durable conversations itself.

**Sessions on a repository (built, [ADR-0027](../adr/0027-start-the-owners-session-on-a-repository-in-a-new-worktree-named-in-code.md), [protocol rule 6a](../specs/protocol.md)):**
- `GET /v1/profiles` lists each profile's repositories with their checkouts' folders. New Session may name one: the profile's, or with no profile one any profile names, and the folder when profiles name it in two. pocketd takes the folder from the profiles (`team.SessionCheckout`), never one the client names alone.
- With `worktree`, the session starts in a new worktree beside the checkout, as a thread's: `<checkout>--<agent>-<slug>` on a new branch `<agent>/<slug>` from the tip of `origin`'s default branch, fetched first, or from `HEAD`, logged, when the fetch fails ([ADR-0056](../adr/0056-start-a-new-worktrees-branch-from-a-fresh-fetch-of-the-remotes-default-branch.md)), `<agent>` the profile's id or `owner`. The slug ends with a suffix of the request id's digest (`proto.SessionWorktree`), so the desktop shows the folder before it sends, a retry finishes the same worktree, and pocketd names it from the request alone. The branch and path are bound to the request's key before git runs (`store.ClaimWorktree`), one worktree a request, with its checkout as git names it, links resolved (`worktree.Top`), and the request id stays the create's, so no other request takes it, through another spelling of the checkout included, and a retry makes none behind a moved link. The request makes the folder alone at its real place, links resolved (`Engine.Real`), in the sandbox (`Engine.MakeDir`), and git makes the branch there or fails (`worktree.AddNew`), in the checkout it bound: a request takes no folder or branch that is there already, and each step is recorded as it is done. git makes it in the sandbox, outside the lock that orders session starts; under that lock, every start reads its profile, and a worktree's is checked again, by the mark its request wrote in its git folder too (`worktree.Usable`, `worktree.Marked`); the agent works at its real place. The desktop waits 6 minutes for such a start (`WorktreeTimeout`). pocketd never removes one.
- Known limit, accepted by the owner on 2026-11-20 and shared with thread worktrees: a folder swapped for another between the `mkdir` that makes a session's worktree folder and the git that fills it cannot be told, since git works by path. A swap needs a process already running as the service user, and the sandbox hides pocketd's files from it.

**Delegation (built):**
- The supervisor delegates a task to a specialist in a thread ([ADR-0014](../adr/0014-delegate-in-threads-with-team-tools-in-code.md), [protocol rules 24 to 30](../specs/protocol.md)). The team tools are Go code in `service/pig`, offered by role: `team_delegate`, `team_close`, `team_schedule`, `team_send`, `team_gather`, `team_board`, `team_launch` and `team_inbox` to a supervisor's session, `team_message` to a thread's specialist session. Each calls `service/internal/api`, which checks the rules in `service/internal/team`, and every step is keyed by the calling session, its tool task and the call's id, so a call run again after a restart finds what it did.
- `team_delegate` records the thread, checks the target's profile again, makes its worktree (marked with the thread, so an older branch of the same name is never reused), starts the specialist's session with the router's model, gives the thread the session, sends the brief, then opens the thread. A thread that cannot start, or is closed while it starts, gets no brief and leaves the desk.
- `team_message` files the report and its asks in one transaction, once per call, puts the asks in the owner's Inbox, and sends the report to the supervisor's session as a message; one that cannot go now is sent again until it does. The owner's answer to an ask reaches the asking session as a message, once; one that cannot go now is sent again until it does.
- Thread and ask events go out with their change, in commit order.
- Each piece of work reports back to whoever assigned it.
- A closed thread's worktree goes ([ADR-0054](../adr/0054-remove-a-closed-threads-worktree-in-code-with-no-github-write.md), [protocol rule 28a](../specs/protocol.md)): every published close queues the thread (`Server.cleanLater`), and the review pass tries it at its end (`Server.cleanPass`), outside the team's locks, once its specialist's and worker's sessions are idle. It takes only a folder named for the thread and never an owner's session worktree, removes it with `git worktree remove` and the local branch with `git branch -d` when the tree is clean and HEAD is in a linked pull request (or, with none, has no commit beyond the branch's start), and otherwise keeps it and names the path and the reason in the thread's report (`team.WorktreeKept`). pocketd writes nothing on GitHub for it.

**The supervisor's message to a thread (built, [ADR-0032](../adr/0032-let-a-supervisor-send-to-a-thread-it-delegated-through-the-outbox.md), [ADR-0037](../adr/0037-unblock-a-thread-when-the-supervisors-message-reaches-it.md), [protocol rule 30a](../specs/protocol.md)):**
- `team_send` sends the specialist of a thread a session of the supervisor's profile delegated, open, done or blocked, a message of at most 6,000 characters, checked in `team.CheckSend` and `team.CheckSendTarget`. It is a row of the outbox to the specialist's session, kept once by the call's key (`team.SendKey`) while the thread is not closed (`store.FileSend`), and placed as an answer is: once, followed until `Engine.Placed` finds it, after the thread's brief, to a watched session; a close withdraws it while queued and drops it.
- Its noting takes a done or blocked thread back to open in the same transaction, with its event (`store.SendDelivered`). A blocked thread's open asks are withdrawn in that transaction, each naming the message, and their events go before the thread's, under `outboxMu` then `workMu` (`Server.sendDelivered`). A withdrawn ask leaves the Inbox, owes the specialist nothing, holds no plan's gate (`team.Gate`), and refuses the owner's answer (`store.ErrWithdrawn`); an answer filed first stands. The message's text ends with a line that states this rule (`team.SendText`), and only a message kept with that text unblocks (`reports.unblocks`); `team_send`'s answer names the asks its own noting withdrew, bounded (`store.AsksWithdrawnBy`). The owner's stop of a shift notes the thread's placed messages, and withdraws its queued ones, before its report (`Server.beforeStop`), and a close that ends a plan notes its lead's. `team_message` notes the thread's placed messages first, under `outboxMu` held through its filing, so a report after a message keeps its state, and so does a close (`Server.sendsBeforeClose`), which also withdraws the plan lead's queued messages when the close may end the plan.
- A shift's round waits for it as for anything owed to the specialist (`store.Owed`), and it pauses nothing. A plan's thread takes one as any thread does; the plan gate is unchanged, but that a withdrawn ask holds nothing.
- Its request key names the supervisor's session (`team.SentBy`), and `service/pig` gives each user entry and queued message it carries a `sender`, which the desktop draws as the supervisor's; a queued message whose sender cannot be read is left out and read again. An older supervisor's session gets the tool at start (`Engine.SetSupervisorTools`).

**The supervisor's view of the owner's Inbox (built, [ADR-0046](../adr/0046-let-the-supervisor-read-the-owners-inbox-from-pocketds-records-in-code.md), [protocol rules 25 and 25a](../specs/protocol.md)):**
- `team_inbox` is a supervisor's alone (`roleTools`), checked again in `Server.TeamInbox` (`team.CheckInboxCaller`). It takes no arguments and writes nothing: in one read transaction (`store.Inbox`) it reads the queries the Inbox's endpoints answer from (those of `store.OpenAsks`, `store.PullsWithReviews`, `store.Plans`, `store.LiveLessons` and `store.PendingApprovals`), the asks answered or withdrawn since 7 days before pocketd's clock and the pull requests merged or closed whose record changed since then (those of `store.SettledAsks` and `store.SettledPulls`, `team.InboxWindow`), and the threads they name, so no item is both waiting and settled. It runs no gh.
- `team.InboxText` writes the answer: what waits for the owner, as the desktop's Inbox counts it (`team.PullWaits` and `team.PlanWaits` mirror `state.ToReview` and `state.ToApprove`), then what was settled, newest first. Each pull request says when pocketd last read it on GitHub, and the first line how often pocketd reads open ones again (`-pr-every`). pocketd keeps no time of a merge or a close: a settled pull request shows its record's last change (`updated_at`), named so: the read that found it merged or closed, or a later change of its title or label.
- The answer is at most `team.MaxInboxBytes` and `team.MaxInboxLines`: a longer one keeps the same number of first items of every list, the most that fit, and says so. The supervisor's instructions tell it to check `team_inbox` before it reminds the owner of an ask or a pull request (`team.InboxGuide`), and so does the tool's description. A supervisor's session started before the tool gets it at start (`Engine.SetSupervisorTools`), a standing one at its idle refresh.

**The question tool (built, [ADR-0048](../adr/0048-put-the-supervisors-and-a-private-agents-questions-to-the-owner-inline-in-code.md), [protocol rules 60 to 62](../specs/protocol.md)):**
- `question` puts a question to the owner inline, in the session, and its call waits for the answer, which is its result in the same run (`team.QuestionResult`). It is no ask and no team tool: a supervisor's or a private profile's session gets it, in an extension of its own after the team tools (`team.MayQuestion`, `toolsOf`), a private one with no team tool; a thread's specialist, a review, a worker, a consult and a gather's session do not, and `Server.Question` checks the caller again with the profile as it is now (`team.CheckQuestionCaller`).
- `team.CheckQuestion` checks the call. Only a run the owner's own message started may ask: `Engine.RunStarter` reads the request key of the submission that placed the run's first entry, and `team.CheckWatched` refuses any key but a device's (`api.ownerMessage`), so a scheduled muster is refused at once. A session has one waiting question, which the work database holds too.
- The wait is an approval's, in `approvals.Questions`: the question is kept by its task and call (`store.QuestionID`, migration 22) before the call waits, a call run again finds it and announces it again, an answer wakes it (`POST /v1/sessions/{id}/question/{qid}`, the first answer standing), an abort, pocketd's start and each end of the session's run skip one whose task ended (`Questions.RetireEnded`, `Server.questionsRunEnded`), and the wait skips one at its deadline, woken by a timer, trying a skip that failed again with a backoff: the profile's `questionMinutes`, else 30 minutes (`team.QuestionTimeout`), on the server's clock. An answer at or after the deadline is refused and skips it (`store.ErrQuestionLate`).
- `team_inbox` lists the sessions whose question waits, by session and profile, never the question's words (`team.Inbox.questionLines`, mirroring `state.Data.QuestionsWaiting`).
- The session carries its waiting question and is `waiting`; each change sends a session event (`Server.publishQuestion`). An older session that gets it now is given it at start (`Engine.SetQuestionTool`), a standing one at its idle refresh.

**Search (built, [ADR-0050](../adr/0050-search-every-session-through-an-fts5-index-in-the-work-database.md), [protocol rule 63](../specs/protocol.md)):**
- `GET /v1/search` finds sessions by their titles and by what their transcripts say: the owner's messages, briefs, reports, answers and a supervisor's messages (user entries), and the agents' replies with their tool calls' names (`search.DocOf`); never thinking, a tool's arguments or its output.
- The index is an FTS5 table in the work database (`search_entries`, migration 23), its rowid the entry's id in `durable.sqlite`, tokenized by `unicode61` with the categories `L* N* Co Mn`, as `proto.SearchWords` splits a query. It is derived from PiG's records: `search.Indexer` reads a session's entries after its cursor (`Engine.EntriesAfter`, 100 at once, in turn with the other sessions) and keeps them with the new cursor in one transaction (`store.IndexEntries`). An entry's event only notes its session (`Server.PublishEntry`), and `StartIndex` starts the indexer after `StartLaunches`, which serving does not wait for; the indexer lists every session itself, the most recently updated first, and again when the list fails: the first start with search reads every transcript in the background, and an answer says `indexing` until it is through. A session whose read or write fails is read again after 5 seconds, doubling with each failure in a row up to 5 minutes (`search.RetryDelay`), the other sessions going on meanwhile.
- Every word of the query begins a word of the entry or title, any case (`search.Match`, `search.Holds`). Hits come newest first, at most the request's limit (50 by default, 200 at most) and 5 of one session's entries, chosen by time from the 20,000 matches last written (`store.SearchEntries`, `search.Arrange`), with `cut` when one was left out. Each has a snippet of at most 160 characters around its first match, with its matches marked as byte ranges (`search.Snippet`).
- Over 200,000 entries in 400 sessions, more than twice today's sessions, `store.SearchEntries` takes under a millisecond for a rare word, 36 ms for a word in nearly every entry and 89 ms for a one-letter prefix (`BenchmarkSearchEntries`).

**Plans and consults (built, [ADR-0020](../adr/0020-plan-before-building-with-the-plan-gate-and-consults-in-code.md), [protocol rules 48 to 54](../specs/protocol.md)):**
- The supervisor starts a plan with `team_delegate` and `plan: {"start": true}`. Its lead plans in its home, in a plan thread that takes no place on the desk; at most 3 plans are open.
- The lead writes the plan with `team_plan`, from the revision it read, drafts its task graph, asks the owner with `team_message`, and consults other specialists. Each call is recorded with its key, in the transaction that checks it. The lead reads files with `read` and GitHub with `team_github` alone ([ADR-0036](../adr/0036-let-proposal-sessions-consults-and-plan-leads-read-github-with-get-calls-built-in-code.md)), and has no worker: it builds nothing. A task's thread is a thread like any, whose specialist may give the work to its worker.
- The plan gate is code. A plan is settled with no open ask, no answer a write has not named, and no consult that runs; a withdrawn ask is neither ([ADR-0037](../adr/0037-unblock-a-thread-when-the-supervisors-message-reaches-it.md)). Ready needs a settled plan and a graph for its revision. The owner approves exactly the revision and graph they saw, from the Inbox. The supervisor delivers each ready task with `team_delegate` and `plan: {"id", "task"}`, and the gate is checked in the transaction that opens the task's thread.
- A task is done when its thread closes with its work done, in the transaction of that close (`store.threadClosed`). The tasks it frees are ready, and the last one makes the plan done.
- A consult is a session pocketd starts from the expert's profile, with exactly `read`, `team_finding` and `team_github` ([ADR-0036](../adr/0036-let-proposal-sessions-consults-and-plan-leads-read-github-with-get-calls-built-in-code.md)): one finding, within 60 minutes of the call. A delivery pass wakes at its deadline. Its question quotes the plan as it stands when the consult starts, since `read` cannot reach the plan.
- Every message pocketd owes for a plan is a note: the supervisor's ready tasks, the consult's question, the finding. Each is keyed and filed with the change that causes it, and placed once (`Engine.Placed`), oldest first per session.

**Shifts (built in the service, [ADR-0024](../adr/0024-run-a-delegated-thread-in-rounds-as-a-shift-driven-in-code.md), [protocol rule 55](../specs/protocol.md)):**
- A supervisor delegates a thread as a shift with `team_delegate`'s `shift`: its task is the objective, with a stop condition, a round limit (20 by default, at most 100), a deadline (at most 24 hours) and, with `ci`, CI green on its pull requests. No spend limit yet: the owner chose rounds and the deadline first.
- pocketd drives the rounds in code (`Server.shiftPass`, one pass at a time, after each run of the specialist or its worker that ends, a round's message or brief noted placed, each pull request round and at start). A round begins at its message's entry, found by its request key (`Engine.PlacedEntry`), and ends when the specialist and its worker are idle and nothing is owed to either, by session (`store.Owed`): a message, a worker's reply, a verdict or an answer. Each decision commits under the shift's lock and `outboxMu` after the round is read again (`commitRound`); a pass that fails retries by itself. Its verdict is the answer's last `STATUS:` line (`team.ParseShiftStatus`); no model judges it.
- The stops, between rounds: blocked, done (with `ci`, each pull request read on GitHub, then its CI, `github.CIChecks`), the same failing checks in three `DONE` rounds in a row, the round limit, the deadline. Each gets one summary round that asks for the specialist's one report, with the status its stop asks for (`team.CheckShiftReport`); until then a final `team_message` is refused. A run that failed, the owner's Stop and the thread's close end it at once. Every end files its report in the transaction that ends the shift.
- The owner's message pauses a shift as it is claimed, before it goes (`store.ClaimSend`); the owner resumes or stops it (`POST /v1/threads/{id}/shift/resume` and `/stop`). A stop ends the shift only (the owner's choice): it withdraws the shift's own queued message and files pocketd's report, and the specialist's and worker's runs go on to their ends. The shift's own lock (`lockShift`) orders a stop, a resume, the owner's message and a round's decision. A round waiting on CI reads it at most once a recheck, and wakes a pass of its own (`wakeForCI`). The desktop shows each shift on its thread's card, with Stop and Resume ([desktop client](#desktop-client)).

**Schedules (built in the service, [ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md), [protocol rule 57](../specs/protocol.md)):**
- The owner's schedules are `schedules.json` in the profile folder, read by `profiles.LoadSchedules` through the pinned folder, each key as written: `{"schedules": [{"id", "when", "zone", "profile", "message"}]}`. An entry that breaks a rule has its problem and goes out never, and the others go out; a file that is no schedules file sends none. An entry goes to its profile's standing session. Its action is a `message` or a `gather` ([ADR-0033](../adr/0033-gather-proposals-from-the-team-in-read-only-sessions-in-code.md)).
- A supervisor's session keeps its own with `team_schedule` (`add`, `list`, `cancel`), offered by role and checked again in `service/internal/api`, an add keyed by its team call, at most 50 a session that still go out.
- A schedules pass (`Server.schedulePass`) runs one at a time: at start, after `engine.Resume` (`Server.StartSchedules`), at the soonest time a schedule goes out, every minute, and after each `team_schedule` call. It reads the owner's file and brings their records in step (`store.SyncOwnerSchedules`), then files each time that is due in one transaction (`store.FireSchedule`): the note `[scheduled] <message>`, keyed `schedule:<owner>:<n>` by the schedule's random owner, and the move to its next time. The delivery pass places the note (`Engine.Placed`).
- A repeat whose last note is not placed skips its time and counts it, once the durable store's record of that note, looked up under `outboxMu`, says it is not in the transcript; a time that goes out once is never skipped. A time missed while pocketd stopped goes out once; a span keeps its beat from the time due. A message to a standing session waits while its profile cannot be applied, as the owner's own message is refused then (`sendOldestNote`, `reconfigureStanding`).
- Clock times are wall-clock times in an entry's zone, else the service's (`TZ`, else `/etc/localtime`'s zone), across daylight saving: a skipped time is the moment after the gap, a time that comes twice the first.
- `GET /v1/schedules` carries the whole list: when each goes next, its counts, what its last time did, and why one does not go out. The `schedules` event says the list changed and carries none, which the client fetches, so the events kept for clients that come back stay small. `team_schedule`'s list comes in pages of at most 16 KiB. A supervisor's session started before `team_schedule` gets it at start (`UpgradeTeamTools`, `Engine.SetSupervisorTools`, which gives such a session every later supervisor tool it lacks: `team_schedule`, `team_send`, `team_gather`, `team_board`, `team_launch` and `team_inbox`), but a standing one, which takes it at its idle refresh; a profile that cannot be read then is tried again at each pass. `pocketd profiles` reports the file entry by entry. The desktop shows no schedules yet.

**Gathers and proposals (built in the service, [ADR-0033](../adr/0033-gather-proposals-from-the-team-in-read-only-sessions-in-code.md), [protocol rules 57 and 58](../specs/protocol.md)):**
- A gather asks agents for proposals: the supervisor's `team_gather`, or a schedule's `gather` action, at its time, for its profile's standing session, which pocketd opens itself when it has none yet (`Server.openStandingFor`), as New Session would. A gather names a skill, read once from the skills folder (`-skills`) as the agents' sandbox shows it (`Server.loadSkill`, `Engine.ReadUpTo`) and kept with it; the skills folder is read-only to agents, so no agent writes another's brief ([ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md)); gather kinds are skills in the owner's configuration, no list in code.
- A launch ([ADR-0034](../adr/0034-launch-the-owners-picks-from-the-supervisors-standing-session-in-code.md)) starts picked proposals as shift threads delegated from the board's supervisor's standing session, until an absolute end: the owner's `POST /v1/launches` or the supervisor's `team_launch`, checked in `team` (`team.LaunchRoom`, `team.CheckLaunchRounds`, `team.LaunchEnd`). The launch pass (`StartLaunches`) starts items in order, at most `team.LaunchAtOnce` at once while the desk keeps `team.LaunchReserve` places free; an item's one thread is created in the transaction that starts it (`store.StartLaunchItem`), its shift with its proposal's stop condition, rounds and `ci` ([ADR-0047](../adr/0047-carry-a-shifts-ci-on-a-proposal-to-its-launch.md)). The desktop's Work Board shows the Proposals section, then the Schedules section, above the threads (`desktop/internal/state`'s `BoardProposals`, `LaunchEnd`, `Store.LaunchPicks`).
- Each agent asked (`team.Askable`) is an ask with a read-only proposal session of its own, started from its profile in its home with `read`, `team_propose` and `team_github` alone (`Server.startAsk`, keyed by the ask's random owner): no place on the desk, no thread. Its brief, the skill's text and the rules of a proposal (`team.ProposalBrief`), is a note filed with the session, placed by the outbox while the ask runs and its 60 minutes last.
- `team_github` ([ADR-0036](../adr/0036-let-proposal-sessions-consults-and-plan-leads-read-github-with-get-calls-built-in-code.md)) reads GitHub's REST API with GET calls alone, for a skill such as an issue triage; a consult and a plan's lead have it too, as the owner chose on 2026-11-21. The agent names a path and query parameters, which `github.Endpoint` checks: a relative REST path of plain segments, never `graphql`, a placeholder or a flag, and a query pocketd encodes. `github.Get` builds every argument, `gh api --hostname github.com --method GET -- <endpoint>`, with no field, body, `--jq` or `--template`, and runs it through `Engine.GH`, in the sandbox with the service user's sign-in, for at most `team.GitHubReadTime`; `Engine.GH` stops gh at its first byte past 1 MiB. `team.GitHubAnswer` compacts its JSON, keeps other text as it came, and cuts an answer over `team.MaxGitHubAnswer` to the whole items of an array, else at a whole character, and says so. `Server.TeamGitHub` checks that its caller is an ask's session, a consult's or a plan's lead (`Server.readsGitHub`). It reads any repository the sign-in reaches, and no count of reads is kept, until the rate limit is hit. At start, a plan's lead made before the tool gets it (`Server.upgradeGitHubTools`, `Engine.SetGitHubTool`); a proposal session or a consult made before keeps its tools. A plan's lead or a consult whose session an earlier run made gets it before its brief or question (`Engine.SetGitHubTool` on the thread's and the consult's start).
- An ask ends at `team_propose done`, when its run ends with its brief in, or at its deadline; the delivery pass follows them (`Server.followGathers`), woken at each run's end, the next deadline and every two minutes. The last ask's end ends the gather and files the supervisor's one note in the same transaction (`store.EndGatherAsk`).

An agent adds, edits and drops its own while its part runs; the supervisor lists, reads, edits, drops and orders its gathers' proposals with `team_board`. Every add, edit, drop and order is keyed by its team call.
- `GET /v1/gathers`, `GET /v1/proposals` and their `gather` and `proposal` events carry them. The board's launch and its desktop section are the next slice.

**Standing sessions (built, [ADR-0026](../adr/0026-keep-the-supervisor-in-one-standing-session-compacted-early-in-code.md), [protocol rules 7c, 7d and 16c](../specs/protocol.md)):**
- A profile with `session: standing` keeps one session for good; only the supervisor's does. New Session with that profile names the profile alone and opens the session: the first one makes it under the engine key `standing:<profile>`, in the profile's folder on the router's model, and records it as the profile's standing session with its request (`store.CreateStandingSession`, work database migration 13).
- At each run end (its busy state ending, its final answer, and, for runs that ended while pocketd stopped, the first delivery pass, `Server.standingPass`), pocketd estimates the session's context (`Engine.CompactIfOver`) and compacts it once it reaches the profile's `compactAt` (`team.ShouldCompact`), in one PiG transaction that finds it idle with no compaction under way and nothing written since the estimate. PiG's own threshold stays every session's backstop, and each model's reserve leaves room for its summary (`summaryReserve`, in `HarnessOptions.Settings`).
- At each run end, before the owner's message, and when New Session or Start Over opens it, the session takes its profile's identity, roster, tools and model as they are now (`Server.reconfigureStanding`, `Engine.Reconfigure`), in one PiG transaction that finds it with no run, keeping its lessons section; it runs whole under `refreshMu`, its reads included, as a lessons refresh does. A session with a run waits for its next idle moment, and refuses the owner's message while its profile's change waits; a profile that cannot be applied refuses it too (`errStandingProfile`). A session that is no standing one never takes `refreshMu`.
- Start Over (`POST /v1/sessions/{id}/start-over`) watches the session, then gives it its profile and writes PiG's reset entry in the same session, keyed by the request, in one transaction that finds it idle (`Engine.StartOver`), so its threads keep reporting there and a Start Over refused changes nothing. It takes the profile's model, never the owner's pick, which PiG drops in the reset's commit, so a Start Over tried again, whose reset is in, drops no pick made since. The transcript shows a compaction as a folded row with its summary, a reset as a note, and a compaction at work as working.

**The owner's model change (built, [ADR-0028](../adr/0028-let-the-owner-change-a-sessions-model-from-the-composer.md), [protocol rule 7e](../specs/protocol.md)):**
- `POST /v1/sessions/{id}/model` changes a session's model, its thinking level, or both. `router.Change` decides, from what the session runs as PiG has it (`Engine.SessionModel`), so a change whose record a stop lost is not undone by the next, and `router.ChangeRule` the route, `owner` once the model changed from the recorded one or from the one PiG ran: the model by the owner's rule, as a New Session's that names one; a level the model takes; without one, the session's level when the new model takes it, else the model's default. A worker's or a cross-review's session is refused, as a message to it is.
- `Engine.SetModel` applies it with PiG's `Configure` in one commit, which keeps the change and its route under the request's key (`pocketgo.model-change`): at once while the session is idle, else from its run's next round. `store.ChangeModel` then records the model, the level and the route `owner` (when the model changed) with the request's completion in one transaction, and the session is published. One change of a session's model runs at a time (`lockModel`), from the read that decides it to its record. The request is claimed before PiG's commit; a failure before it frees the claim (`releaseModel`), and one after keeps it. A failure before PiG's commit frees a claim an earlier try left too, or, for one that stops before it could tell, leaves it to a delivery pass (`releasePending`). A retry answers the session as it is, without changing it again, and publishes it again, since a stop after the record may have kept the first event from going (`store.ChangeModel` reads nothing after its commit): one whose change PiG has, from a try that stopped before its record, records it while it is the session's latest change (`pocketgo.model-last-change`) and PiG runs it, else what PiG runs then, whose record a stop may have lost too, so a later change or a Start Over stays (`recordModel`); a retry of one that completed records what PiG runs first (`recordRunning`). The first delivery pass looks at the claims a stop left (`store.LeftClaims`) and frees each PiG has no change of. A Start Over records the level PiG runs, and the owner's route while PiG keeps a pick of the model it runs (`recordStandingModel`).
- In a standing session the change is the owner's pick, kept in PiG with the change that applies it (`pocketgo.pick`, `Engine.StandingPick`) and made under `refreshMu`, so no refresh comes between. Every refresh gives the session the pick's model in place of its profile's model, at the pick's level while the model takes it, else at its default (`standingSpec`, through `router.Change`), until Start Over drops it. A pick whose model's window cannot hold the profile's `compactAt` is refused, one whose profile cannot be read now is `internal`, and one while pocketd runs without profiles, or whose profile folder is no longer the one it protects (`profiles.ErrFolderChanged`), is `conflict`. `changeFor` applies the spec's level, so a refresh keeps the pick's and takes the default again after Start Over; PiG reads a level it does not hold as off.
- A cross-review keeps the author's model its reviewer was chosen by, as PiG runs it, read under the author's `lockModel` (`threads.review_author_*`, work database migration 15, which gives each review under way its author's session's model then), for its start and for its verdict's family check, so the owner's change of the author's model counts from the next review.

**Attachments (built, [ADR-0029](../adr/0029-attach-the-owners-files-to-a-message-stored-outside-the-data-folder.md), [protocol rule 10a](../specs/protocol.md)):**
- `POST /v1/sessions/{id}/uploads?name=<name>&requestId=<id>` takes a file's bytes as its body, at most 50 MiB: the one route whose body is not JSON, bounded by `proto.MaxUpload` where every other is by 1 MiB. A worker's or a cross-review's session takes none (`Server.noComposer`), as it takes no message.
- `service/internal/uploads` keeps the file in `~/.local/share/pocketgo-uploads/<session>/<stamp>-<random>-<name>` of the service user, outside the data folder, where the sandbox shows it to the agents, read-only (`Sandbox.Shown`, [ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md); `Sandbox.Hides`, which pocketd warns on at its start). Agents could write there before ADR-0035, and the owner still can, so pocketd follows no link and never waits on what was put there: it opens each folder below `~/.local/share` by its descriptor with `O_DIRECTORY|O_NOFOLLOW|O_NONBLOCK`, the service user's, made 0700 again when it was open to others (`openSub`); writes a new file unnamed (`O_TMPFILE`), else in a staging folder in the data folder, which no agent reaches, with its bytes' SHA-256, and names it once whole, where no entry is, the name and each folder it is in, made or found, synced to disk before the upload counts (`Stage`, `Staged.Link`, `syncDir`; a sync that fails after the name is `ErrNotSynced`, which keeps the claim), the file found at the upload's path before it is stored (`Folder.Names`; a session's folder an agent moved drops the claim, a check that fails keeps it), an upload that could never be named refused before its body is read (`ErrStagingElsewhere`, a staging folder on another file system, or on Linux another mount: `mountOf`, from `statx` or the descriptor's `fdinfo`), the body bounded in time (`UploadBodyTimeout`), the next start clearing what a stop left there: only regular files named as pocketd stages one, through the folder's descriptor, not through a link (`ClearStaging`); tells what a name holds by `fstatat` before it opens it; and reads one only as the regular file its name holds in its session's folder, never through a link, at most its upload's size, and for a model only as the bytes whose SHA-256 it kept when it staged them (`ReadUpload`, ADR-0035). It removes nothing there. The safe name and the type are pi-pocket's (`SafeName`, `Mime`).
- `store.ClaimUpload` claims the upload with its request and this run's token, pending, before its file is written; `store.StageUpload` keeps its file's device, inode and size before the name; `store.FinishUpload` stores it once named (work database migration 18, `uploads`). An upload that fails before the name drops its claim and leaves nothing (`uploads.ErrNameTaken` for a name an entry holds); one a stop cut off is settled by the same request tried again, or by the next start's first delivery pass, which finds it by its run and skips a key a request holds: finished while its name holds the file pocketd staged (`Folder.Holds`, which tells another file by its entry before it opens one, and writes the name to disk, in the folder whose entry names it then, before it says so), else dropped, whatever the name holds (`settleLeftUploads`). A retry answers the upload the first try stored, once its body was read to its end under the upload's bound. A message with its files' lines stays within `proto.MaxComposedMessage`, checked before any image is read, so its entry event is readable, and its images within `uploads.MaxMessageImages` of base64, past which an image is named alone. The first pass skips a key a request holds and stays due for a later pass (`keyLocks.tryLock`, which reserves the key as it finds it free).
- `SendMessage.attachments` names uploads of the session by id (`store.SessionUploads`). The message ends with `Attached files (saved on the server):` and a line for each file, sent as blocks of their own apart from the owner's words (`api.Attached`, `pig.userContent`); `pig.attachedText` joins them back as `proto.WithAttachments` writes them, which `proto.SplitAttachments` reads back for the desktop, and counts the files from those blocks alone (`Entry.Files`), so a list the owner wrote stays words. An entry is read from its message's Go value, never copying its images (`userBlocks`), and a read or a watch of a session holds at most `recordsAtOnce` records (`entriesBetween`, `viewWindow`), as each may hold a message's images. Every message carries its images: a PNG, JPEG, GIF or WebP of at most 5 MiB that decodes whole (a GIF's first frame alone, on its canvas, made PNG or JPEG) goes after the text as PiG's `ai.ImageContent` (`Engine.Send`), fitted by `uploads.PrepareImage` within 2,000 pixels a side and 4.5 MiB of base64 (an image not opaque as PNG alone), by halving and then bilinear, so its memory stays near the image's own; a JPEG whose EXIF orientation is not upright (`proto.JPEGOrientation`, 2 to 8) is turned upright after it shrinks (`proto.Upright`) and never goes as it is, since models do not read EXIF, so a phone photo reaches the model upright, its sizes the upright image's; its line notes what changed. One that cannot go is named with a note why. The model that reads the message, when it runs, gets its images as images when it takes images (`Model.Images`, PiG's catalog input), and any other model PiG's placeholder in their place (`ai.TransformMessages`, at each request), so no model change gives a model content it cannot take. A retry of a message that went reads nothing again. The message is made before the lock of the shift whose specialist takes it, so no image holds up a stop or a round's decision. A user entry counts its images (`Entry.Images`).

The verdict closes the review thread, and the author's thread hears it once; the supervisor is not told.
- After a verdict, and at every round, `Server.syncReady` keeps `ready-for-human` in step: it reads CI at the head for a ready verdict, and writes the label only when it must change. A linked pull request carries the label's state, CI's state and the newest verdict at its head, base branch and merge base to the desktop, which shows them on its cards; a merge base that moved since the verdict, or that GitHub does not name, leaves none. ### Policies enforced in code

Every rule below is service code with tests; prompts only inform agents of them. A model's output that feeds a decision is structured output that code validates, and code decides.

- **Cross-review (built, [ADR-0017](../adr/0017-record-cross-review-verdicts-and-set-ready-for-human-in-code.md), [ADR-0019](../adr/0019-start-each-cross-review-in-code-with-the-authors-agent-on-the-reviewer-model.md)):** pocketd starts each review in code, one a head, within the owner's budget; the review thread files a structured verdict (`ready`, `not-ready`, `unclear`) with `team_verdict`. Code refuses one from the author's thread, from the author's model family (`router.Family`, the model's maker), or at a head that is not the pull request's head on GitHub.
- **The plan gate (built, [ADR-0020](../adr/0020-plan-before-building-with-the-plan-gate-and-consults-in-code.md)):** a plan is settled when no ask is open, every answer is written into the plan, and no consult runs. The owner approves an exact revision with its task graph, and a task is delivered only while it is ready in the approved graph, checked in the transaction that opens its thread.
- **Approve or merge:** the shared bot account never does both on one pull request. pocketd itself writes only the label: no review, approval or merge. Approve and merge as the owner, from the desktop, is next (Phase 2, slice 6b).
- **`ready-for-human` (built, ADR-0017):** pocketd puts the label on a linked open pull request, no draft, exactly while the newest verdict at its head is `ready` and CI there is green (`pr-triage` left out), and takes it off otherwise, whoever put it on: a head that moves takes it off. Core's `pr-triage` removes it on a push too.
- **Leases:** on shared test resources.
- **Private agents:** they work only in sessions the owner starts in their home. They take no delegation and report to nobody (built: `team.CheckDelegation`). Their sessions have their own preamble, no roster, no lessons section and no team tool, and every team tool refuses them before it runs, an older session's included (built: `team.PrivateIntro`, `roleTools`, `Server.TeamAllows`, [ADR-0042](../adr/0042-give-a-private-agent-its-own-preamble-and-no-team-in-its-sessions.md)).
- **Questions (built, [ADR-0048](../adr/0048-put-the-supervisors-and-a-private-agents-questions-to-the-owner-inline-in-code.md)):** only a supervisor's or a private agent's session puts a question to the owner, only in a run the owner's own message started, one at a time, skipped at its deadline (`team.MayQuestion`, `team.CheckWatched`, `team.QuestionTimeout`).
- **The desk:** at most `-desk-cap` threads that are not closed (built). A plan's own thread takes no place on it, and at most 3 plans are open (built).
- **Per-profile limits:** on MCP servers and tools.

### Desktop client

The desktop client is built on MyGo and frostui, in the `desktop` module. It talks to `pocketd` only through `proto` ([specs/protocol.md](../specs/protocol.md)).

**Built (Phases 1 to 3):**
- **`desktop/internal/state`:** the data layer and state, with no UI import (a depguard rule in `.golangci.yml` refuses MyGo and frostui there), so a phone client can reuse it ([ADR-0010](../adr/0010-port-the-desktop-client-selectively-from-frostyard-pocket.md)). Every rule in it is code with a test ([ADR-0011](../adr/0011-put-rules-in-code-not-in-model-judgment.md)):
  - **`Store`:** one sign-in. Each request runs on a goroutine and posts its result to the UI thread. Answers of an earlier sign-in are dropped, and a 401 signs out.
  - **`Link`:** the event stream. When it drops, it waits as `Backoff` says (1 s, doubling to 30 s, on an injected clock) and reconnects with `Last-Event-ID` set to the last event applied. The store fetches the sessions, the pending approvals, the open asks, the lessons, the threads, their pull requests, the profiles and the open session when a stream opens with no event to come back from, and on `resync`. A stream that comes back from an event, the `hello`'s included, misses nothing, so the store fetches again only what failed to load. No fetch waits for the `hello`, which an older `pocketd` never sends.
  - **`Data`:** what the client knows. An event that arrives while a fetch is in flight wins over that fetch's copy. The answer of a fetch begun before one already applied is dropped, per list and per session summary, which both the list and a session's detail carry. A session moves up the list with the session event that follows each of its entries. The messages a session holds for a run show queued at the end of its transcript, from its live state. Each list records whether its last fetch failed, so the Inbox never says that nothing waits when it does not know (`InboxNote`). A session with a pending approval shows as waiting. The open asks merge by the same rule as the approvals, and so do the threads and their linked pull requests, except that a closed thread and a merged pull request stay in their lists. A thread held with a later `updatedAt` than a fetch's copy also stays: pocketd moves it with each change, never back.
  - **The board's rule (`Data.NextMover`):** a thread is grouped by who moves it next. Nobody moves a closed thread. The owner moves one with an open ask, with an open pull request that is no draft (`ToReview`), or whose plan waits for their approval (`ToApprove`). Otherwise the owner moves one whose shift the owner's message paused, and its specialist one whose shift runs or asks for its summary, whatever its last report said. Otherwise its specialist moves it while it starts or is open, and its supervisor once the specialist reported it done or blocked. `Data.BoardNote` claims a count of the threads on the desk only when they loaded, and how many wait for the owner only when the asks and the pull requests loaded too.
  - **Which pull requests show (`Data.Pulls`):** as `GET /v1/pulls` lists them, the open ones and those of the threads not closed, whichever order the merge's and the close's events came in.
  - **Plans (`Data.Plans`, `PlanSeen`):** plans merge by the threads' rule. A plan waits for the owner only in review, settled, with the graph drafted for its revision, and an approval names that revision and that graph version. An approval tried again unchanged keeps its request id, and an approval of a plan that changed since is a new request. The reply is never applied: the plan's event, or the fetch that follows, brings it. `Data.OnTheDesk` leaves a plan's own thread out, as pocketd's cap does.
  - **Shifts (`ShiftLine`, `CanStopShift`, `CanResumeShift`, [ADR-0024](../adr/0024-run-a-delegated-thread-in-rounds-as-a-shift-driven-in-code.md)):** a shift's line says its round of its limit, its deadline while it runs, and why it paused or ended. The owner may stop a shift that has not ended, and resume one that paused, or ended for a reason other than done, its deadline or its thread's close, while it has rounds left, as protocol rule 55 has it; neither shows on a thread that is starting, has no session or is closed, which pocketd refuses. pocketd checks a deadline that passed since, and the brief. A stop or resume keeps its request id only while it is tried again on the shift as the owner saw it (its state, reason and round): one on a shift that moved since is a new request, and once an event, a fetch or its own reply shows the shift moved, its failure goes too (`Store.settleShifts`). Its reply is the thread: the copy with the later `updatedAt` wins, since pocketd moves it with each change, never back; a held copy as old that differs is fetched again, and so are the threads when a fetch of them is in flight (`Data.ThreadChanged`).
  - **Standing sessions (`NewSessionRequest`, `OpenableProfiles`, `StartOverBlocked`, `StartOver`, [ADR-0026](../adr/0026-keep-the-supervisor-in-one-standing-session-compacted-early-in-code.md)):** New Session on a standing profile, labeled "· standing session", sends the profile alone and opens its session; a standing profile whose session the desktop knows is offered whatever its problem. Start Over is offered only to a standing session whose detail loaded, with no reload failed since, and showed no run and nothing waiting (`Live.pending`), asks first, is checked again as it is sent, and its request id is kept for a retry only until the session writes another entry, so a later Start Over is never a replay of the first.
  - **Sessions on a repository (`RepositoryChoices`, `SessionFolder`, `WorktreePreview`, `Store.NextCreateID`, [ADR-0027](../adr/0027-start-the-owners-session-on-a-repository-in-a-new-worktree-named-in-code.md)):** New Session offers the chosen profile's repositories, or with No profile every repository a profile names, each folder once and labeled with it when a name has two; a standing or private profile, or one pocketd no longer offers, offers none. Choosing one fills in its folder, a folder typed by hand ends the choice, and None brings back the folder typed, else the one of the profile chosen now. With the worktree switch on, the form shows the folder and branch pocketd will make, named from the request id it will send (`requestIDs.Peek`, which `For` then takes), so a retry of a failed start shows and finishes the same worktree.
  - **The model chip (`ChipOf`, `Store.ChangeModel`, [ADR-0028](../adr/0028-let-the-owner-change-a-sessions-model-from-the-composer.md)):** frostyard/pocket's, whole. The chip in the composer's row names the session's model, its id when the models do not name it, and a level other than off; its menu has a submenu per provider, in the order `GET /v1/models` lists them, with the current model checked, and a Thinking submenu when the model takes more than one level, an empty level reading as off. Two models of one provider with the same name, or a name that is another model's id there, are told apart by their ids, and each item is keyed by its model, so a choice in a menu the list changed under goes to the model chosen. A session with no composer, a worker's or a review's, has no chip. A change tried again unchanged keeps its request id until the session is seen with another model, level or route than when it went (`settleModels`); its answer shows as the session's event would, and a change that failed says why above the composer. No message goes while a change is on its way (`Store.MaySend`). The models load again with every Refresh and every stream that comes back, through `Data.SetModels`, so an answer older than one applied never applies, and the chip offers to load them again when their list failed to load.
  - **Attachments (`Store.Attach`, `Store.AttachPicked`, `Store.Attachments`, `Store.AttachmentsReady`, `FileSource`, `UploadType`, [ADR-0029](../adr/0029-attach-the-owners-files-to-a-message-stored-outside-the-data-folder.md)):** frostyard/pocket's, whole. A file attached in the composer is a chip at once, uploading, then uploaded or failed, its upload's request id its chip's own; a chip removed stops its upload, and one that failed offers Try Again, which uploads it from the same source with the same request id (`Store.RetryAttachment`), so pocketd answers an upload it stored whose answer was lost; its bytes are a snapshot the desktop copied as the file was attached, off the UI thread, read to its end, at most 50 MiB, whatever size the file said, so a retry sends what was attached under a request id kept for its digest, and pocketd's own redirect replays them (`proto.Client.Upload`'s opener, only to the same origin, `proto.SameOrigin`, which `state.SameOrigin` is, with the same method). At most `MaxAttachWork` files hold a file open at once, being copied or uploaded, or kept for Try Again after a failed upload; the others wait their turn; a Try Again of a kept copy goes ahead, and a removal takes its chip out of the line at once and frees its slot once the copy or upload under way ends, as a sign-out does (`runAttach`). Pasted files waiting their turn keep at most `PastedWaitingLimit` bytes; a paste past it fails at once (`ErrTooMuchWaiting`), and so does one whose copy cannot be made, keeping none of its bytes. An upload's turn ends once its file is let go and its answer settled, taken or dropped with its sign-in, a 401's sign-out included (`dropAnswer`). A redirect the client follows keeps the token (`checkRedirect`). A copy is one of `snapshots`, a file with no name on disk from the moment it is made (`createSnapshot`: removed at once on Unix; on Windows opened by no other handle and removed at once where the file system takes POSIX deletion, else as it closes), so a crash leaves nothing; uploads read it through its one handle, and it goes once its upload is done, its chip is removed, the owner signs out or the store closes, as its last reader ends. A pasted image's bytes go once its copy is made; pasted bytes over the limit fail at once with no Try Again (`Attachment.Retry`). Files the chooser gave after the sign-in changed are not attached (`ErrSignInChanged`). A message waits until every chip uploaded (`MaySend`), carries the uploads' ids, may be files alone, and keeps its request id when tried again with the same text and files, told apart by the text's length; its chips leave once pocketd took it. A file attaches only as a regular file of at most 50 MB, opened without waiting on a named pipe, of its extension's type, else its bytes'. `BuildRows` splits the owner's message into its words and the files pocketd named (`proto.SplitAttachments`), with the images it gave the model; a supervisor's message (`Row.Sender`), and a queued preview cut short, shows its text whole, as pocketd names files only in the owner's message, whole.

A start that failed without pocketd's answer keeps its request id until one comes, whatever the list does: tried again, even at the cap, pocketd answers the shell it started, or `not_found` once that is gone, and the store then starts another with a new id. A shell this window started shows its whole output live, without the replay, so its login's queries are answered (`Store.TakeFresh`); one started and not listed yet shows as starting (`Data.TerminalAwaited`), and while a start is on its way, a shell its event lists shows only once the answer says whose it is (`Store.AttachReady`). Keys a server or a gateway failed to take are sent again, with their number, until `sendFor`; pocketd's refusal below 500 is final. The title a shell's history set names its tab, though only the history's screen reaches the emulator. The first poll reads the history pocketd kept at once (`wait=0`), so what comes after it is live and a query in it is answered; the history is drawn off-screen up to a character or an escape sequence it ends in the middle of; the rest goes to the live emulator with what completes it (`SplitReplay`). Only web and mail links a shell prints open (`SafeLink`).

One that fails stays with its reason; Stop ends the run after the merge under way. A dependency bot's `risk:high` pull request joins the list without Open Diff (the owner's choice of 2026-11-21): a `Bot` whose login is on `github.DependencyBot`'s list in code (`dependabot`, `renovate`), which Act checks again on each read; an agents' App, any other author, and a card's merge still need the diff. Such a waived merge is bound to the base commit its check read, so once a turn merged, each later waived pull request of the run on that branch is checked again at its own turn, at the new base, through every gate, and merges bound to the new base commit or stays with why ([ADR-0038](../adr/0038-check-bot-pull-requests-again-in-the-run-once-a-merge-moves-their-base.md), the owner's choice of 2026-11-21); the Inbox's bar says when it checks one again. A dependency bot's pull request that an earlier merge of the run, seen to land, left in conflict with its base, or behind it where the rules need it up to date, or whose mergeability GitHub has not computed there yet, at the head and base branch the owner confirmed, is no failure: the summary counts it apart, and lists it after the failures, as waiting for its bot to rebase it, by the bot's name ("2 wait for Dependabot to rebase"; `state.rebaseWait`, the bot from `github.DependencyBotOf` as the check read it, the refusing read's head and base from `github.Result`, and the branch the run's merge went into from its `MergedInto`); one whose base no merge of the run moved stays a failure ([ADR-0039](../adr/0039-count-a-bots-pull-request-the-run-left-in-conflict-as-waiting-for-its-rebase.md), the owner's choice of 2026-11-21). The rules are in `state.GitHub` (`desktop/internal/state/mergeall.go`); `app` draws them.

**Data layer:** the client's data layer and state are built on `proto`, kept apart from desktop-only views (tray, the terminal's emulator, native sign-in flows); a terminal's connection and its rules are in the data layer. The iPad builds them as they are, on MyGo's iOS target, and `make portable` builds them for `ios/arm64` in CI ([ADR-0040](../adr/0040-build-the-ipad-and-iphone-client-from-the-desktops-code-on-mygos-ios-target.md), [plan: phone and tablet client](../plans/phone-client.md)).

### Execution adapters

Both adapters implement PiG's `durableenv.ExecutionEnv`: files, exec and watch, with terminals separate.

- **Local:** a git worktree on the service host (built for threads and the owner's sessions: `service/internal/worktree`). Its commands run in pocketd's bubblewrap sandbox ([ADR-0012](../adr/0012-run-tools-without-approval-in-a-sandbox-that-hides-pocketds-files.md)), which hides pocketd's files but is not a boundary between agents.
- **Coder:**
  - **Connection:** `env.ConnectionOptions.CommandFunc` runs `coder ssh <workspace> -- pi-env serve`. Templates include a `pi-env` built from the PiG commit the service pins.
  - **Lifecycle:** the service creates, starts and stops workspaces through Coder's REST API, as a Coder service account.
  - **Prebuilds** give warm starts, and **Boundary** limits network egress.
  - **No model credential** enters a workspace.

## Operational notes

- **Where it runs:** `pocketd` runs on the team VM under systemd, as user `team`, the way `pi-pocket@.service` runs today.
- **Deploy:** `make deploy DEPLOY_HOST=team@<vm>` (over ssh), or `make deploy DEPLOY_INCUS=<remote>:<instance> DEPLOY_INCUS_PROJECT=<project> DEPLOY_USER=team` (over `incus exec`, acting as the user with `runuser` and that user's systemd), runs `deploy/deploy.sh`. The script builds `pocketd` for the host's architecture, installs it as `~/.local/bin/pocketd`, installs `deploy/systemd/pocketd.service` as a systemd user unit of that user, and restarts it. Settings go in `~/.config/pocketd.env`, for example `TZ=<zone>` for the zone of the schedules' clock times that name none ([ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md)). `POCKETD_LISTEN=<address>:<port>` moves pocketd off its loopback default, only where no proxy fronts it: on the team VM it stays unset, behind `tailscale serve` (see how clients reach pocketd, below). The owner's own commands (`pocketd login`, `pocketd device`) must use the same data folder: pass `-data` when the env file sets `POCKETD_DATA`. The unit is `Type=notify`: pocketd reports ready once its start order completes, so a failed start fails the deploy. The user needs lingering (`loginctl enable-linger`) so the service runs with nobody logged in. Re-running the target upgrades in place.
- **Data folder:** `-data` (default `$POCKETD_DATA`, else `~/.local/state/pocketgo`) holds `durable.sqlite`, `work.sqlite` and `auth.json`, and `upload-staging`, where an attached file is written whole before its name on a file system without unnamed files (ADR-0029). `-listen` defaults to `127.0.0.1:8788`.
- **How clients reach pocketd:** on the team VM, pocketd listens on that default, and `tailscale serve --bg --https=443 http://127.0.0.1:8788` (run as root) serves it to the tailnet at `https://<host>.<tailnet>.ts.net`. Clients sign in at that address; nothing listens on the tailnet's port 8788 ([plan: phone and tablet client, Phase 1](../plans/phone-client.md#phase-1--pocketd-over-https-on-the-tailnet-small)).
- **Uploads folder** ([ADR-0029](../adr/0029-attach-the-owners-files-to-a-message-stored-outside-the-data-folder.md)): the owner's attached files are in the service user's `~/.local/share/pocketgo-uploads/<session>/`, outside the data folder, so the agents read them in the sandbox. The folder is read-only to agents ([ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md)). pocketd never removes one: the owner removes them by hand, from a terminal or over ssh. A folder removed whole is made again, empty, before the next command. They are not part of the data folder's backup, and the work database's `uploads` rows name them by file.
- **Sign-ins:** `pocketd login PROVIDER` writes the data folder's own `auth.json`, in Pi's format. It never shares Pi's file: two processes refreshing one OAuth refresh token can sign each other out.
- **One process per data folder.** If two ran on one store, durable tasks would run twice. `pocketd serve` takes an exclusive `flock` on `pocketd.lock` in the data folder and refuses to start without it.
- **Start order:**
  1. take the lock
  2. check the sandbox: trial commands under `bwrap`, or no start
  3. bind the port
  4. open the work database and the harness, with no task running yet
  5. wire the API and the team, deny pending approvals of ended tasks, and watch every session
  6. resume tasks
  7. start the first delivery pass over reports, answers and briefs that did not reach their session, which serving does not wait for
  8. start the pull requests' rounds and the schedules' passes ([ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md)), which serving does not wait for either
- **Stop order:** on SIGTERM, end the event streams and the delivery passes (waiting for one that runs), shut down HTTP (10 seconds), then close the harness (20 seconds). Running tasks resume at the next start.
- **Agents and the sign-ins:** `service/pig`'s guarded environment wraps PiG's local one.
  - Every file access checks the path PiG will open, after normalization and symbolic links, and refuses the data folder.
  - Every command gets an allowlisted environment, never pocketd's.
  - Model credentials come only from the stored sign-ins; environment and file credential sources are disabled.
  - Every command runs under `bwrap` (`service/pig/sandbox.go`, [ADR-0012](../adr/0012-run-tools-without-approval-in-a-sandbox-that-hides-pocketds-files.md)):
    - the data folder and `/run/user`, which holds the runtime folders with the D-Bus and systemd sockets, are empty `tmpfs` mounts, under every path a mount shows them at. On the VM, `/home` is a bind mount of `/var/home`.
    - pocketd's program, `~/.config/pocketd.env`, the user's systemd configuration and the agents' profile folder are read-only
    - the skills folder (`-skills`, `~/.pi/agent/skills` by default) and the uploads folder are read-only too, but shown ([ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md), `Sandbox.Shown`). pocketd keeps each where it found it (`Sandbox.keepShown`), before each command and every quarter of a second (`Sandbox.watchShown`, which an engine with a sandbox runs until it closes). One the owner removed or replaced outside the sandbox took the read-only binds of the commands running then with it, so pocketd first kills every `bwrap` it started (`stopSandboxes`, only through a pidfd: no pidfd, no signal, and the stop fails), then, once that succeeded, makes a missing folder again, empty, and keeps another one from then on; a stop that failed, or a sandbox it could not look at again, is tried at the next look. Each kept folder is held open, without following a link or waiting on a pipe, so its inode cannot be used again while it is kept; a path a mount shows a single file at is held as that file (`Sandbox.roots` are the folders pocketd named). At every look it reads the mount table again (`Sandbox.mounts`, `unkeptAlias`), and a mount that shows a folder, or a part of one, where the sandbox does not keep it read-only, or a table that shows no mount a folder is on, stops every command and file-tool change until a restart. The paths a mount shows a folder at come from the mount the kernel walks to (`mountAt`), only where that mount is the one seen; a table with no mount a protected path is on stops the start. A stop holds a pidfd of each `bwrap` that carries the sandbox's random mark (`--setenv POCKETD_SANDBOX`, so a `bwrap` the owner starts is never one) and of its namespace's first process, kills both, and waits until all have ended (`waitEnded`, at most 10 seconds); what has not ended is waited for again at the next stop (`pendingStops`), and a stop that failed is done again at every look until one succeeds (`keptFolders.unfinished`); a sandbox is held whole, its `bwrap` and its first process, or not at all; paths are held with `O_PATH`. Every command starts through pocketd's own gate in the sandbox (`pig.GateHelper`), which runs it only when every path a mount shows a shown folder at, and every mount seen inside one but the sandbox's masks, is read-only there, so a command admitted before a new mount and started after it refuses to run. The gate finds each shown folder by its place as well, device and path inside its filesystem (`placesOf`), so one a mask hides is checked wherever a mount shows its files; when a mask hides pocketd's program, that mask shows the program alone, read-only, as `.pocketd-gate`, for the gate and for every command that runs pocketd's program, a gather's read helper included. A path a mask hides is no alias: neither bound nor watched, nor a cause to stop commands. `Engine.Close` waits for the watch to end, within its context, at every call. A command or a file tool's change waits for the look only until its context ends (`Sandbox.CommandContext`), and the file tools know a read-only folder by its identity too, so another spelling of its name, as a filesystem that ignores case gives, changes nothing. A look that stopped commands looks again before it acts, and makes a missing folder without following a link; each shown folder is kept as the kernel spells it, as are the hidden and read-only paths, verified against the open file; a rename or removal acts on the entry, so a link to an upload may go. A `bwrap` with no first process held is left running for the next stop, and a path a mount no longer shows a folder at stops commands until a restart. The pinned folders above each shown folder are kept as the folders are (`Sandbox.watched`), a stop a change asks for comes before any failure is reported, and the gathers and the uploads use each folder as the sandbox keeps it, links resolved (`newSandbox` rewrites the names `pocketd serve` passes). Missing folders pocketd named are made before the paths a mount showed them at are looked at again. A link that stands on the way to either since the start stops every command until a restart. A command running when the owner replaces a folder can still write in the new one until pocketd sees the change.
    - the owner's global instructions file (`-instructions`, `~/.pi/agent/AGENTS.md` by default) is kept as a shown folder is, as a single file ([ADR-0045](../adr/0045-make-the-global-instructions-file-read-only-to-agents.md), `Sandbox.files`): bound read-only under every path a mount shows it at, the folders above it pinned, looked at before each command and every quarter of a second, proved by the gate and the start check. pocketd makes it at its start when it is missing, an empty regular file of mode 0600, without following a link and never truncating one that is there (`makeFileNoFollow`), and again once the commands stopped when the owner removed it; a folder or another kind of file at its path stops the start. The owner's write in place, as the install script's `cp`, keeps the same file: nothing stops, and running commands and the next new session read the new text. A replacement by rename is a replaced shown root: every running command is stopped first, then the new file is kept. Only the file is kept, not `~/.pi/agent`, where Pi's programs write; `-instructions ""` keeps none.
    - every folder above them that the user could rename is bound onto itself, so it cannot be renamed or removed, under every path a mount shows a protected tree at
    - the command sees only its own processes
    - everything else, the network included, is as the service user has it: the VM is the boundary
  - The file tools refuse the same paths, through links too, and a rename or removal refuses a folder that holds one. They read the skills folder, the uploads folder and the global instructions file, but refuse to change anything in them (`guardedEnv.readOnly`; the file's refusal is `errReadOnlyFile`, the paths the sandbox checked, never resolved again), and change nothing at all while a link put on the way to one since the start leads it elsewhere (`guardedEnv.redirected`), or while the sandbox stops commands (`keepShown`).
  - What agents could change before the folders were read-only is not taken on trust: an upload's image goes to a model only as the bytes whose SHA-256 pocketd kept when it staged the file (`uploads.ReadUpload`, `uploads.ErrChanged`); a gather refuses a skill whose file has another name (a hard link), through which it could still change (`pig.ReadHelper` answers `linked`, `api.ErrManyNames`); and the owner syncs the skills folder once again after deploying ADR-0035. A global `AGENTS.md` with another name is left out of the instructions with a note (`team.GlobalSection`, [ADR-0045](../adr/0045-make-the-global-instructions-file-read-only-to-agents.md)).
  - A symbolic link the user can change on the way to a protected name, the skills folder, the uploads folder and the global instructions file included, stops the start, and so does a link in the systemd folders to a file the user can change.
  - Before binding, `pocketd serve` proves the sandbox: `bwrap` must show itself as process 1, every hidden path empty, and every read-only path, the two shown folders and the global instructions file included, on a read-only mount in the sandbox's own mount table (`mountAt`, which walks the table as the kernel walks the path).
  - No tool call waits for the owner, except one that asked under an earlier rule. The host needs bubblewrap, installed by the system, and unprivileged user namespaces (`apt install bubblewrap` on Debian). pocketd uses only a `bwrap` that root alone can change, and `pocketd serve` refuses to start without a working one.
- **The owner's terminals and the agents:** an agent's command runs as the same user, and the agents' sandbox shows the host's `/dev/pts`: while a shell runs, an agent's command can open its pseudo-terminal, read what the owner types there and print on the owner's screen. Hiding `/dev/pts` in the agents' sandbox would close that; the owner accepted the exposure on 2026-11-20 and left the sandbox as it is (ADR-0025).
- **The owner's terminals** ([ADR-0025](../adr/0025-give-the-owner-a-shell-on-the-service-host-from-the-desktop.md)): shells run as the service user, outside the agents' sandbox, within pocketd's systemd unit: with its `UMask=0077` and `NoNewPrivileges=yes`, so `sudo` does not work in them, and they end when pocketd stops or restarts, a deploy included. A device token is a shell: revoke a lost device's token at once (`pocketd device revoke NAME`).
- **Coexisting with pi-pocket:** while both run on the VM, they never share a data folder or a store.
- **Restore the data folder as a whole.** `durable.sqlite` and `work.sqlite` describe one state: the threads, asks and reports of the one name the conversations and submissions of the other. Stop pocketd and copy, or restore, the folder at once. pocketd takes care that a key from one never names the wrong object in the other (thread owners, ask keys, answer digests, attempt checks), but it does not reconcile one database restored to an earlier point than the other.
- **Back up separately, never in this repository:**
  - the data folder's two databases, `durable.sqlite` and `work.sqlite`, as one item: stop pocketd, then copy both
  - provider sign-ins
  - the Coder service-account token
  - the GitHub App token
- **The Coder adapter** needs the `coder` CLI on the VM, signed in as the service account.
