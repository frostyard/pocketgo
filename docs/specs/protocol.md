# Spec: pocketgo protocol, version 33

This spec defines the HTTP protocol between `pocketd` and its clients: the desktop client now, and a phone client later. The Go types in `proto/` are its machine form. `service/internal/api` serves it, and `proto.Client` calls it. A change to this spec lands in the same pull request as those three.

## Interface

### Every request

| Header | Required | Value |
| --- | --- | --- |
| `Pocket-Protocol` | yes | `33` (`proto.Version`) |
| `Authorization` | yes | `Bearer <device token>` (`pocketd device add NAME` prints one) |
| `Content-Type` | with a body | `application/json`; an upload's, the file's type (rule 10a) |

Bodies are JSON objects of the `proto` type named below, but an upload's, which is the file's bytes (rule 10a). Times are RFC 3339 in UTC.

### Errors

Every non-2xx answer has an `Error` body: `{"code": "...", "message": "..."}`.

| Status | `code` | When |
| --- | --- | --- |
| 400 | `protocol` | `Pocket-Protocol` is missing or is not `33` (`proto.Version`) |
| 401 | `unauthorized` | the token is missing, malformed, unknown or revoked; a failure to check it is 500 |
| 400 | `bad_request` | the body, a path value or a query value breaks a rule below, as a search's `q` or `limit` (rule 63), or a usage report's `since` (rule 64), or a rename of a session that is no private agent's now (rule 68), or a start or sign-out of a provider that signs in on the service host alone (rule 69) |
| 404 | `not_found` | no session, approval, thread, ask, lesson, plan, listed pull request or listed terminal with that id, no question with that id in the session (rule 62), no change of the session's checkout that names the path, or no checkout (rule 67), no provider pocketd signs in to, no device flow it keeps, or a start whose flow a restart lost (rule 69), or no route for the path |
| 405 | `bad_request` | the path exists, but not for that method |
| 413 | `bad_request` | an upload's file is over 52,428,800 bytes (`proto.MaxUpload`, rule 10a) |
| 409 | `conflict` | a new session's worktree whose path another request holds (rule 6a), a Start Over of a session that has a run or messages waiting (rule 7d), the owner's message to a standing session whose profile cannot be applied, or that is at work while its profile's change waits (rule 7c), a change of the model of, or an upload to, a worker's or a cross-review's session (rule 10a), or of a standing session while the service runs without profiles (rule 7e), a pull request was read again while `GET /v1/pulls/{id}` checked it, the approval is already decided, the ask is already answered or was withdrawn (rule 30a; the message says which), the question is already answered or skipped (rule 62; the message says on which device, or why), a lesson decision does not hold (rule 33: changed since seen, nothing to decide, gone, or its agent's lessons full; the message says which), a plan's approval does not hold (rule 50; the message says why), a terminal's start, keys or size does not hold (rule 56: 4 shells run, the shell exited, 16 clients type into it, or the service stops; the message says which), a session's checkout git cannot read isolated (rule 66; the message says why), a rename while the profile folder is no longer the one the service protects (rule 68), a device flow's start while the service stops (rule 69), the owner's message to a `closed` thread's specialist that cannot reopen it (rule 10; the message says why, and where to send it instead), or the `requestId` was already used for a different request |
| 500 | `internal` | the service failed |

### Events

`GET /v1/events` streams Server-Sent Events. Each event has:
- `id:` the event's `seq`
- `event:` its `type`
- `data:` the JSON of `proto.Event`

| `type` | Payload field | Sent when |
| --- | --- | --- |
| `hello` | — | the stream opens; always its first event (rule 18) |
| `session` | `session` | a session is created, its `state` changes, an entry of it is written, its question is put, answered or skipped (rule 60), or it is renamed (rule 68) |
| `entry` | `entry` | a transcript entry is written |
| `live` | `live` | a session's live state changes, its queue of messages included; `live` replaces the previous one whole |
| `approval` | `approval` | an approval is requested or decided |
| `thread` | `thread` | a thread is delegated, starts, gets a report, closes, reopens (rule 24), or names its successor (rule 26) |
| `ask` | `ask` | an ask is put to the owner, answered, or withdrawn (rule 30a) |
| `lesson` | `lesson` | a lesson is written, changed by its agent, or decided by the owner |
| `pull` | `pull` | a pull request is linked to its thread, pocketd reads a change of it on GitHub, or its thread reopens (rule 24) |
| `plan` | `plan` | a plan starts, or its text, its gate, its graph, its tasks or its consults change (rule 54) |
| `schedules` | `schedules` | a schedule goes out, skips or misses a time, is added or cancelled, or the owner's schedules file changes what the list says (rule 57); it carries no list: the client fetches `GET /v1/schedules` |
| `gather` | `gather` | a gather starts, an ask of it starts or ends, a proposal of it is filed, changed or dropped, or it ends (rule 58) |
| `proposal` | `proposal` | a proposal is filed, edited, ordered, dropped, launched, started as its thread, or back on the board (rules 58 and 59) |
| `launch` | `launch` | a launch starts, an item of it starts or is skipped, or it ends (rule 59) |
| `signin` | `signin` | a provider's device flow starts or ends, or pocketd signs in to it or out of it from a client (rule 69); it carries the provider's sign-in as `GET /v1/signins` lists it |
| `terminals` | `terminals` | a terminal starts, exits, ends, or leaves the list (rule 56); it carries the whole list, oldest first, and leaves the field out when none is listed |
| `resync` | — | the events after the client's `Last-Event-ID` are gone |

## Rules

**Authentication**
1. The service refuses a request without `Pocket-Protocol: 33` before it checks the token. Version 5 added each agent's lessons (rules 31 to 35). Version 6 added the pull requests linked to threads (rules 36 to 40). Version 7 added cross-review verdicts and `ready-for-human` (rules 41 to 45). Version 8 starts each cross-review in the service and gives a pull request's verdict on its head and base branch (rule 46): a desktop that merges on the head alone is refused. Version 12 adds a thread's shift and its stop and resume (rule 55). Version 13 adds the owner's terminals (rule 56). A client of one version cannot work with a service of another, so each side refuses the other's version.
2. A device token is `pgd_` followed by 64 hexadecimal characters. The service stores only its SHA-256, and a revoked token gets 401.

**Request bodies**
3. A request body is one JSON object, but an upload's (rule 10a). Unknown fields, trailing data and bodies over 1 MiB are `bad_request`.

**Request ids**
4. Every `POST` but a terminal's `input` and `resize` (rule 56) carries a `requestId` of 1 to 128 bytes: in its body, and an upload's, whose body is the file, in its query string (rule 10a). The service scopes it to the device: the same id from two devices is two requests.
5. A retried `POST` with the same `requestId` from the same device does nothing twice:
   - `CreateSession` answers 200 with the session the first call created, even if its `cwd` or model has gone away since. A first call that made its new worktree (rule 6a) and failed after it leaves the worktree, and the retry finishes it, makes no other, and starts the session there.
   - `StartOver` answers 200 with the session once its reset is in, even if the session has a run since (rule 7d). Its `requestId` is claimed for that session before the reset: one that finds the session at work, or that fails with no reset in, frees it; one that fails after its reset keeps it, so the client retries the same Start Over with it, and another request with it is `conflict`. A Start Over at work whose freeing fails says so (`internal`, with a message that the `requestId` could not be freed yet), and the service frees it later while it runs, never one whose reset is in.
   - `SendMessage` answers with the same `submissionId`.
   - `Upload` answers 200 with the upload the first call stored, and stores no other file (rule 10a).
   - `ChangeModel` answers 200 with the session as it is now (rule 7e). Its `requestId` is claimed before the change, which the service keeps with it in PiG, with its route: one that fails with no change in frees it, at once or, when it stops before it could tell, later while it runs, a claim a stop of the service left included; a retry after one whose change went never changes the session again: it records the change while it is the session's latest and the session runs it, else what the session runs then, so a later change or a Start Over stays; a retry of one that completed records what the session runs then, before it answers.
   - `RenameSession` answers 200 with the session as it is now, renames nothing again, and publishes the session again (rule 68).
   - `Abort` records the run it targets (by the run's first entry) before it acts, then waits up to 15 seconds for the run to settle. A retry finishes that abort and never stops a run started after the first call. A settled abort answers 200 on every retry.
   - `Decide` answers with the decided approval.
   - `AnswerAsk` answers with the answered ask.
   - `AnswerQuestion` answers with the question as it is (rule 62).
   - `ApprovePlan` answers with the plan as it is (rule 50).
   - `StartSignIn` answers 200 with the flow the first call started or answered, as it is now, and starts no other: the service records the `requestId` with the new flow's id before the flow is made, published or polled, whether or not the client is still there, and a start whose record fails is `internal` and starts nothing. Once a restart or a later start lost that flow it is `not_found`, and the client starts another with a new `requestId` (rule 69).
   - `CancelSignIn` answers 200 with its flow as it is now, and cancels nothing else: its `requestId` is recorded with its flow before the cancel, so one whose record fails is `internal` and cancels nothing, and the `requestId` reused for another flow is `conflict` (rule 69).
   - `StartTerminal` answers 200 with the terminal the first call started while its shell runs, and starts no other; once that shell is gone, or when it never started, it is `not_found`, and the client starts another with a new `requestId` (rule 56).
   - `CloseThread` answers with the thread, as it is now: a close that committed closes nothing again, though a message reopened the thread since (rule 24). Its `requestId` is reserved before the close withdraws a queued brief: a close that fails with no withdrawal taken effect frees it, and one that fails after a withdrawal keeps it, so the client retries the same close with the same `requestId`, never another request. A close whose freeing of its `requestId` fails says so (`internal`, with a message that the `requestId` could not be freed yet), and the service frees it later while it runs, never one a close completed since. A restart before then leaves the `requestId` held: the same close with it still works, and another request with it is `conflict` (a known limit; the desktop never reuses a `requestId` for another request).

   A `requestId` already used for another endpoint or another target is `conflict`. Requests of one `requestId` run one at a time, on every endpoint, so of two that share it one takes effect. A close checks its `requestId` before its thread, so one used for another request is `conflict` even for a thread that does not exist. A request that failed leaves no record, so its `requestId` is free again, but for a `CreateSession` that bound its new worktree (rule 6a): its `requestId` stays that `CreateSession`'s, and another request with it is `conflict`. A session's conversation records the request that created it, so a retry after a failure between the two stores finds that conversation instead of creating another.

**Creating a session**
6. `CreateSession.cwd` is an absolute path to an existing directory on the service host. The service cleans it, for example by removing a trailing `/`. With a `profile`, an empty `cwd` is the profile's `home`, else its `workspace`.
6a. `CreateSession.repository` names a repository, `owner/name` as `GET /v1/profiles` lists it, its name in any case ([ADR-0027](../adr/0027-start-the-owners-session-on-a-repository-in-a-new-worktree-named-in-code.md)): with a `profile`, one the profile names; without, one any valid profile names. The session works in its checkout, the folder a profile names for it, which must be an existing directory: `cwd` is then empty or that folder. Without a profile, the profiles may name the repository in more than one folder, and `cwd` names which; empty is then `bad_request`. A repository the profile does not name, one no profile names, and a `cwd` no profile names for it are `bad_request`: the service takes no folder for a repository but a profile's.
   - With `worktree`, the session works in a new git worktree of that checkout, made by the service: `<checkout>--<agent>-<slug>`, on a new branch `<agent>/<slug>` from the tip of the checkout's `origin` default branch, fetched first as rule 26 says, or from its `HEAD` when that fails ([ADR-0056](../adr/0056-start-a-new-worktrees-branch-from-a-fresh-fetch-of-the-remotes-default-branch.md)). `<agent>` is the profile's id, or `owner` (`proto.OwnerAgent`) without a profile. `<slug>` is the trimmed `title`'s lowercase ASCII letters and digits as words joined by `-`, whole words while the next and a `-` fit in 40 characters (`session` when none does), then `-` and the request's suffix: the first 6 characters of the lowercase base32 (RFC 4648, no padding) of the SHA-256 of the `requestId`. `proto.SessionWorktree` computes it, so a client shows the folder and branch before it sends, and the service names them from the request alone, never from a path the client sent.
   - The worktree's branch and path, its checkout as git names it, and its real place (its folder's parent with every link on its way followed, then its name) are bound to the request's key (its device and `requestId`) before git runs, for good, with the `requestId` (rule 5), and a request makes one worktree: a retry finishes the worktree an earlier try of it made (rule 5); a retry whose checkout or place moved since, by its path, by a link above it, or with a `cwd` naming the old folder, is `conflict`; and another request whose branch, path or place comes out the same, through another spelling of the checkout included, is `conflict`. A `CreateSession` with the same `requestId` and no `worktree` is another request: `conflict`, also once the worktree's session is recorded; so is one with a `worktree` after one with the same `requestId` and none started its session.
   - A branch that is there is `conflict` before anything is made. The request then makes the worktree's folder alone, at its real place, in the sandbox, with a `mkdir` only root can change, and git makes its branch there or fails, in the checkout the request bound, never one a link names later: a folder that is there, or a branch another made as git ran, with nothing of git's in the folder, was made by something else (another data folder, a service racing for the name, or a work database restored from before), and the request is `conflict` on its first try and every one after, never handed it; git that failed keeps its word; one that left the branch there, whoever made it, is `conflict`, since no retry can take the name, and any other failure of git's is `bad_request`. git's worktree is then marked as the request's: a new folder, `pocketgo-request-` and a digest of the request's key, in the worktree's own git folder, made with the same `mkdir`, which refuses every entry that is there, and which git removes with the worktree. Each step, the folder, git's worktree and its mark, is recorded as it is done, before any check that may fail after it (a record that fails is `internal`). A retry of a request whose git made its worktree checks that worktree as it is, and by its mark, and never makes or marks it again: one made again at its place, on its branch, or never marked, is not provably the request's, and is `conflict`, as is one whose mark was there before the request marked it; such a refusal is recorded, so no later try takes the worktree, whatever is marked there since. A retry whose checkout moved is told so before its new folder is looked at. A retry whose earlier try made only the folder is `conflict`, since another folder may be in its place by then. A start cut off between a step and its record, or after the folder alone, leaves a folder or a worktree no retry takes; the owner looks at it before removing anything. The checkout and the place are resolved from one resolution of the folder they share. A `CreateSession` with the `requestId` of one that bound its worktree but naming another `profile`, `repository`, `cwd` or `title` is another request: `conflict`, compared as named, with nothing read again.
   - Once the worktree is made, which may take minutes, the service checks it again as it is then (its checkout's and its folder's paths still naming the checkout and the place it was made at, else `conflict`; git's registered worktree there, on its branch, not locked, and marked as the request's; within 30 seconds), then reads the profile, the profiles and the models again, last, and starts the session only from what they say then, with the same checkout and worktree, at the worktree's real place, which the session lists as its `cwd`: a request they no longer take is `bad_request`, one whose checkout the profiles no longer name is `conflict`, as its retry would be, and the worktree stays.
   - It is made and checked as a thread's is (rule 26): the checkout must be the top of its repository; a worktree at the path must be git's registered one there, on its branch with a commit, and not locked. git runs in the sandbox (rule 14e), to its end or 5 minutes, also when the client goes away. A worktree or checkout git says is not as it must be is `bad_request` with git's word for it; a check that could not tell is `internal`, with why. The service never removes a session's worktree.
   - `worktree` without a `repository` is `bad_request`. So is a `repository` or a `worktree` for a standing profile (rule 7c), and for a `private` profile a folder that is not its `home` (rule 7b).

7d. `POST /v1/sessions/{id}/start-over` gives a standing session a fresh context in the same session: the service watches it first, then, in one step, gives it its profile as rule 7c says (a profile that cannot be applied leaves the agent as it is) and writes a `reset` entry, keyed by the request, and the model sees nothing before it. The service records the model the session runs then, as PiG has it, with its level, and the route `owner` while a pick of that model holds, before the request completes.

The session of a thread's worker (rule 47) and of a cross-review (rule 46) is `conflict`, as a message to it is. The service applies the change at once while the session is idle; during a run, from the run's next round, after the model's current answer and the tools it called. Two changes of one session's model, with other `requestId`s, run one at a time, so the recorded model is the one the session runs. In a standing session (rule 7c) the change is the owner's pick: the route becomes `owner` in any case, and the pick holds in place of the profile's model, through every time the session takes its profile, until the owner changes it again or the session starts over (rule 7d). A pick whose model's `contextWindow` is not above the profile's `compactAt` is `bad_request`, since the profile could no longer be applied; one whose profile the service cannot read now is `internal`, and one while the service runs without profiles, or while its profile folder is no longer the one it protects, is `conflict`, as the owner's message to the session is (rule 7c); none changes anything. A retry with the same `requestId` answers the session as it is now, without changing it again, and publishes the session again (rule 5); the id reused with another body, or for another session, is `conflict`. A cross-review under way keeps the author's model it was chosen by (rules 42 and 46).

10a. An upload is a file the owner attaches to a message ([ADR-0029](../adr/0029-attach-the-owners-files-to-a-message-stored-outside-the-data-folder.md)). `POST /v1/sessions/{id}/uploads?name=<name>&requestId=<id>` stores one for the session. Its body is the file's bytes, at most 52,428,800 (`proto.MaxUpload`): a longer one, by its `Content-Length` or as it is read, is 413. The body, a retry's included, arrives within 10 minutes of the request's start (`api.UploadBodyTimeout`), or the request ends. A worker's (rule 47) or a cross-review's session (rule 46) takes no upload (`conflict`), as it takes no message.
   - The service keeps the file in `~/.local/share/pocketgo-uploads/<session>/` of the service user, outside its data folder, where a command in the sandbox can read it but not change it, nor can the file tools (rule 14e). Its name there is `<stamp>-<random>-<name>`: `<stamp>` is the service's time in milliseconds since 1970 in base 36, and `<random>` is 8 hexadecimal characters. `<name>` is `name`'s last path element with each run of characters other than ASCII letters, digits, `_`, `.`, `-`, space, `(` and `)` made one `_`, and trimmed; `upload` comes before it when it is empty or starts with `.`, and it is cut to 120 bytes, so a name made safe twice stays as it was. The file has mode 0600, its folders 0700: a folder of the service user's that is open to others is made 0700, and one another user owns is refused (`internal`).
   - The service follows no symbolic link there, and never waits on what was put there, by an agent before the folder was read-only to agents or by the owner. It opens each folder below `~/.local/share` by its descriptor, as a folder, not through a link and without waiting on a named pipe. It writes a new file with no name (`O_TMPFILE`), else in a staging folder in its data folder, which the sandbox hides, and names it in the session's folder only once it is whole, where no entry is; an upload whose name an entry holds already makes nothing and removes nothing. The name, and each folder it is in, made or found, are written to disk (the folder's `fsync`) before the upload is stored; a name whose write failed keeps its upload staged, for the same request tried again or the next start to finish. The file must then be at the upload's path, its session's folder as the uploads folder names it now: one whose folder an agent moved as it was named is not stored (`internal`), its claim dropped, and the request tried again stores it anew; the moved file stays. One whose path could not be checked keeps its claim, for the same request tried again or the next start to settle. Where the uploads folder's file system makes no unnamed file and the staging folder is on another file system, or on Linux another mount (its id as `statx` or the descriptor's `fdinfo` gives it; a folder whose mount neither gives is refused too), an upload is refused (`internal`) before its body is read, since the staged file could never be named. It tells what a name holds without opening it, so a socket there is no file. A file it reads must be the regular file its name holds in the session's folder, never one a link there leads to, read without waiting on a named pipe and at most to its upload's size. The service removes nothing there: uploads stay until the owner removes them.
   - The upload's type is `Content-Type` without its parameters, in lowercase, when it is a type (`type/subtype`) of at most 255 bytes (`proto.MaxMimeType`) other than `application/octet-stream`. Otherwise it is the type the service's own table gives the name's extension (`proto.UploadMime`, as the name is `proto.SafeUploadName`), else `application/octet-stream`.
   - The file and its record, keyed by the request (rule 5), are kept together. The upload is claimed, pending, before its file is written; staged, with its file's device, inode, size and SHA-256, once the file is whole and before it is named; and stored once it is named. An upload cut off before its end is `bad_request`, and one that fails or is refused before its name leaves neither. One a stop of the service cut off is settled by the same request tried again, or by the first delivery pass of the next start, under the request's key, skipping one a request holds until a later pass: finished, and answered, while its name holds the file the service staged, of its bytes, its name written to disk first in the folder whose entry names it then, else dropped, whatever the name holds. Whether the name holds another file is told by its entry before the file is opened, so one the service may not read is another. The next start also clears what an earlier run left in the staging folder: the regular files named as the service stages one (16 hexadecimal characters, `-`, and 16 more), through the folder's descriptor, not through a link; anything else there stays. The next start finds them by the run of the service that claimed them, not by the clock.
   - The answer is `Upload`: its `id`, its `sessionId`, its `name`, its `mimeType`, its `size` in bytes and its `path` on the service host. A new upload is 201, a retry 200 (rule 5), once its body was read to its end under the same bound: one over it is 413 and one cut off `bad_request`, whatever its `Content-Length` says. `proto.Client.Upload` sends the file again on a redirect only to the same origin, with the same method, whatever HTTP client it runs on, checked again after that client's own check of the redirect, and with its token; the file it opened again for a redirect it does not follow is closed: the same scheme in any case; the same host as the resolver looks it up, an ASCII name in any ASCII case, a final dot kept, since a name with one skips the search list and may name another machine, an IP address exactly, its zone included, and any other name byte for byte; and the same port, a scheme's default counted (`proto.SameOrigin`, which the desktop's `state.SameOrigin` is).
   - `SendMessage.attachments` names uploads by their `id`, in order; an id named twice counts once. Each must be a stored upload of that session (`bad_request`). The session gets the text, then the line `Attached files (saved on the server):` as a block of its own and a line for each file from its record, `- <path> (<name>, <mimeType>, <size> bytes)`, with a note for an image, as another block, apart from the owner's words; its user entry's `text`, and its queued message's, joins them as `proto.WithAttachments` writes them, a blank line before the heading, and its `files` counts the files (rule 16a). A text of white space alone is left out, with its blank line. A client reads files' lines only where `files` says the message attached files: a list the owner wrote or pasted is words, a user entry or a queued message with a `sender` shows its text whole, since the service names files only in the owner's message, and so does a queued message's preview cut short (`cut`), which may end within its files' lines.
   - An attachment whose `mimeType` is `image/png`, `image/jpeg`, `image/gif` or `image/webp`, of at most 5,242,880 bytes, also goes with the message as an image. The model that reads the message, when it runs, gets it as an image when that model has `images` (rule 7a); any other model gets `(image omitted: model does not support images)` in its place, at each of its requests, so a model change before the message runs, or after, gives no model content it cannot take. Its format is the one its bytes have, among those four, and its whole image must decode. A message with its files' lines has at most 1,048,576 bytes (`proto.MaxComposedMessage`, `bad_request`), so its entry stays readable on the event stream; one too long reads no image. A message's images take at most 24 MiB of base64 (`uploads.MaxMessageImages`): an image past that goes without its image, its line noting `[Image: not shown to you: the message's images reach their 24 MiB.]`. A retry of a message that went reads its files no more (rule 5); one whose claim paused a shift (rule 55) is made again, its files read, while the service does not have its message. A message refused for its attachments, one that names an upload not of its session or one too long with its files' lines, frees a claim an earlier try left, as rule 5 frees a refused request's; its attachments are read once whether it went is known. The message is made, its files read and its images fitted, before the lock of the shift whose specialist's session takes it (rule 55), which no image holds up.
   - It goes as it is when its sides are at most 2,000 pixels and its base64 is below 4.5 MiB, but a GIF: its first frame alone, drawn where it stands on the GIF's canvas, the rest of which shows the GIF's background color, goes as PNG or JPEG, and its other frames are never decoded. Nor does a JPEG go as it is whose first EXIF segment, before its first scan, names an orientation of 2 to 8 (tag 0x0112, a SHORT or a LONG of one value; `proto.JPEGOrientation`): models do not read EXIF, so the service turns and mirrors it upright, as a viewer shows it (`proto.Upright`), then sends it as PNG or JPEG as below, whatever its size; its sizes, in the notes too, are the upright image's. Any other orientation, or EXIF it cannot read, is upright; a PNG's or a WebP's EXIF is not read. Otherwise the service fits it within 2,000 pixels a side, as PNG or as JPEG at quality 80, the smaller first, then as JPEG at quality 70, 55 and 40, and then a quarter smaller each time, until its base64 is below 4.5 MiB; an image that is not opaque goes as PNG alone, since JPEG drops its alpha. Its line notes `[Image: shown to you as <PNG or JPEG>.]` when its format changed, and `[Image: original <w>x<h>, displayed at <w>x<h>. Multiply coordinates by <factor> to map to original image.]` when its size did, or `Multiply x coordinates by <factor> and y coordinates by <factor>` when its sides' factors differ. The service fits an image by halving it while a side is more than twice its target, then bilinear, so the memory it takes stays near the image's own; it turns a JPEG upright after it shrinks it, for the same reason.

So does one whose bytes are not those it was uploaded with, checked against the SHA-256 the service kept when it staged the file, as one an agent changed before the uploads folder was read-only (rule 14e): `its file changed since it was uploaded`.

**Approvals**
12. No tool call waits for an approval: `NeedsApproval` selects no tool ([ADR-0012](../adr/0012-run-tools-without-approval-in-a-sandbox-that-hides-pocketds-files.md)). A call of a tool it selects waits for an approval, as rules 13 to 15 describe, and so does a call that asked for one under an earlier rule.

14. An approval is decided once. Deciding it again with a new `requestId` is `conflict`. `Decide.allow` is required: a body without a boolean `allow` is `bad_request`, never a denial.
14a. Once an aborted run settles, its pending approvals whose tasks ended are denied, with `decidedBy` `pocketd`; a run started since keeps its own. At start, the service also denies each pending approval whose task has ended. Approval events leave in the order the approvals changed.
14b. No file access by a tool reaches the service's data folder, which holds the sign-ins. The service checks the path the environment will open, after its own normalization (relative paths, `~`, `file://` URLs) and after resolving symbolic links, at the moment of access. The refusal is an error tool result.
14c. A tool's command gets only an allowlist of the service's environment variables (`PATH`, `HOME`, `USER`, locale, temporary and XDG folders, and Go's `GOPATH`, `GOCACHE`, `GOMODCACHE` and `GOFLAGS`), plus what the tool sets. Provider keys never reach it.
14d. `GET /v1/models` lists only the models of providers with a stored sign-in. An API key in the service's environment neither lists a model nor runs a session. A model whose provider's stored sign-in is an API key is listed like any other, and runs any session ([ADR-0022](../adr/0022-run-any-session-on-any-sign-in-and-choose-workers-from-the-owners-list.md)), for a provider `pocketd login` keeps a key for (rule 47); a key of another provider, as one written by hand, lists nothing, since its adapter may not be linked. The owner's own providers, `providers.json` in the profile folder, and the models it adds to the service's own providers (`builtinModels`, each run as the catalog's model it is `like`, under its own id, and never one the catalog has) are listed too ([ADR-0023](../adr/0023-add-the-owners-own-model-providers-from-a-file-checked-in-code.md)): one that takes no key at once, sending the placeholder key `none`, one that takes a key once it is stored; a stored API key counts only as stored, from one read, and only when it is a literal one, never run as a command or read from the environment; an owner's provider's request goes through no proxy and follows no redirect to another origin; a file that breaks a rule registers none of them, and the service starts without them.
14e. Every command a tool runs goes through the sandbox. In it, the service's data folder and `/run/user` are empty, under every path a mount shows them at. The service's program and the files that decide its next start are read-only, the folders above them cannot be renamed or removed, and the command sees only its own processes. The file tools refuse the same paths, through links too, and a rename or removal refuses a folder that holds one. The skills folder (rule 57) and the uploads folder (rule 10a) are read-only too, under every path a mount shows them at, and the folders above them cannot be renamed or removed, but a command and the file tools read them ([ADR-0035](../adr/0035-make-the-skills-and-uploads-folders-read-only-to-agents.md)): a file tool's write, append, truncation, flush or new folder in one, through links too, a rename or removal of an entry in one, a rename into one, and a rename or removal of a folder that holds one are error tool results. The service makes either folder when it is missing, empty, at its start; a symbolic link the service user can change on the way to either stops its start. It uses each as the sandbox keeps it, links resolved. Before each command and every quarter of a second, it looks at both and at the pinned folders above them: when one is missing, is another folder than the one it kept, or has a link on the way to it, every command running in the sandbox is killed first, since a folder removed or renamed outside takes their read-only binds with it, only through a pidfd, only a `bwrap` that carries the sandbox's own random mark, with the first process of its namespace, and the stop is done once all have ended: where no pidfd opens, or one has not ended within 10 seconds, the stop fails, and the next look stops and waits again; once it succeeded, a missing one is made again, empty, and another one is kept from then on, held open. At each look the mount table is read again: a mount that shows either, or a part of one, where the sandbox does not keep it read-only, or a table that shows no mount one is on, stops each command until it goes or a restart, as a link on the way does; the file tools change nothing at all meanwhile. Each command starts through the service's own gate in the sandbox, which runs it only when every path a mount shows either folder at, and every mount seen inside one but the sandbox's own masks, is read-only there, and else ends with exit status 125; a path a mount no longer shows a folder at stops each command until a restart. A skill whose file has another name (a hard link), through which it could change, is none (rule 57), and an image goes to a model only as the bytes it was uploaded with (rule 16a). The service refuses to start unless a trial in the sandbox shows `bwrap` as process 1, every hidden path empty, and every read-only path, the two folders included, on a mount whose own options are `ro` in the sandbox's mount table; a path a mask hides is not tried. The owner's global instructions file (`-instructions`, which every new session's instructions hold) is kept read-only in the same way, as a single file, and the folders above it cannot be renamed or removed ([ADR-0045](../adr/0045-make-the-global-instructions-file-read-only-to-agents.md)): the service makes it at its start when it is missing, an empty regular file, without following a link and never truncating one that is there; a folder or any other kind of file at its path stops the start; a file tool's write, append, truncation or flush of it, a rename onto it, its removal or rename, and a rename or removal of a folder that holds it are error tool results, through links and other names too. A write in place on the host keeps the same file and stops nothing; a replacement by rename or a removal stops every running command first, as for a folder, then keeps the new or newly made file. A global instructions file with more than one name (a hard link) is left out of a session's instructions with a note. `-instructions ""` keeps no file.

**Transcripts**
16. Entry ids grow in the order entries are written. `SessionDetail.entries` lists every entry, by ascending id.
16a. A `user` entry carries the `submissionId` of the message that placed it, the one `SendMessage` answered with, both in `SessionDetail.entries` and in its `entry` event, `images`, how many images the message gave the model (rule 10a), when it gave any, and `files`, how many files the owner's message attached, when it attached any; a queued message carries its `files` too. The service counts them from the blocks it sent, never from the text: a block of the heading alone, followed by a block of lines that name files. A message sent while the session runs waits for a run: `Live.queued` lists it, with its `submissionId` and text, oldest first. It leaves the queue when a run reaches it and writes its entry, whose `entry` event comes before the `live` event without it.
   - An abort of a running session withdraws its queued messages, and they get no entry. A run that fails keeps them queued, with the session idle; an abort then does nothing, and the next message's run takes them first.
   - `Live.queued` lists at most 100 messages (`proto.MaxQueuedListed`), each with its first 4,096 bytes of text cut at a character (`MaxQueuedText`, with `cut` set), and `queuedMore` counts the newer ones it leaves out. The message's entry has all of its text.
   - A user entry and a queued message that are not the owner's carry `sender`: `{"kind": "supervisor", "session": <id>}` for a supervisor's message (rule 30a), its `session` the supervisor's session that sent it. The service sets it from the request key of the submission that placed or carries the message, which only its own outbox writes, never from the text; the owner's message carries none, whatever its text says, and so does every other message the service places. A queued message whose submission the service could not read is never listed without its sender: a `live` event leaves it out and lists it in a later live state once it can, which the service reads again within seconds whether or not the session changes, and `GET /v1/sessions/{id}` fails (`internal`) until it can. The service reads the senders of the 100 oldest queued messages alone.
   - `SessionDetail` reads its `live` and its `entries` at one revision: the entries through the newest one the live state saw, so a queued message is in one of them.
   - When the service fails to read a watched session, it sends none of the new entries and not the live state that follows them, and reads again within seconds.
16b. Each `entry` event is followed by a `session` event of the entry's session, with the `updatedAt` the entry set and the `usage` it added. Session events leave in the order the service read the sessions, so the last one is current. A session event the service fails to read, the usage included, is read again within seconds until it goes out; a summary with no usage never goes out in its place. So is the write of the entry's time: the entry goes out and its time is noted at once, the summary waits for the write, and never goes out with the time before the entry. A retried write sets the time the entry had, never a later one, and never moves a session back. A new session is watched and its creation event goes out even when reading the answer to `CreateSession` fails; a retry of the request answers it.

16c. A `compaction` entry carries, as its `text`, the summary that stands for the context before it; a `reset` entry starts the context afresh (rule 7d). Neither deletes an entry. `Live.compacting` is set while a compaction of the session's context runs, and `Live.compactionFailure` says why the newest one failed, until one succeeds. `Live.pending` is set while anything waits for a run, a write `queued` does not list included, as a compaction's summary that waits for its run's end.

**Event stream**
17. Event `seq` numbers grow across service restarts, even when the clock moves back: the service reserves them in the work database in blocks, and never sends a number outside a reservation. When a reservation fails, the event is dropped and every stream ends. Each client resyncs, also one whose `Last-Event-ID` is the event before the dropped one. The service keeps no events across a restart: each process starts at numbers of its own, inside its first reservation, and a `Last-Event-ID` from before them resyncs. Some numbers go to no event (a process's start, a `hello`'s); they are reserved too.
18. Every stream starts with one `hello` event. A client sends the `seq` of the last event it applied, the `hello`'s included, as `Last-Event-ID` when it reconnects.
   - Without `Last-Event-ID`, `hello` carries the newest event's `seq`. A client that reconnects with it misses nothing, even when no other event came first.
   - On reconnect, a client sends `Last-Event-ID: <seq>`. `hello` carries that same `seq`. The service then sends every kept event after it.
   - If those events are gone, or `seq` is in the future, a single `resync` follows `hello`, and the client refetches what it shows. This `hello` carries a `seq` that resyncs for as long as the service runs, from before its first event or a lost one: a client that loses the stream before `resync` comes back with it and gets `resync` again. The client's own `seq` would not do when it is in the future, since the service may have given it out by then. The `resync` carries the newest `seq`, always past that boundary: right after a lost event it is a fresh number, so a client that applied it reconnects without another resync.
   - A client that comes back fetches again what had not loaded when the stream dropped, a refetch still in flight included: it is past the events that would bring what it missed.
19. The service sends `: keepalive` comment lines every 10 seconds while the stream is idle. At each one, it checks the stream's token: a revoked device's stream ends within 10 seconds. A service that stops ends every stream first. Each write has a 10-second deadline, so a client that stops reading cannot hold its stream open.
20. The service drops a client that falls 256 events behind; the client reconnects with `Last-Event-ID`.

**Profiles**

21. `GET /v1/profiles` lists every `<id>.md` file of the profile folder, by id; other files, such as backups, are not profiles. The service reads a profile only as a regular file in that folder with no other name, never through a symbolic link or a hard link, and never waits on a named pipe. The frontmatter is one YAML document. A valid profile lists its fields, `standing` and `compactAt` included (rule 7c), and `questionMinutes` (rule 60), and its `repositories` by name, each a `name` and the `folder` of its checkout (rule 6a); `cwd`, the folder a session from it starts in by default (its `home`, else its workspace); and `runs`, the model a session from it runs now, as the router chooses it. A profile that breaks a rule, or that no sign-in serves, or that names a tool the service does not have, or that is private with a home that is not a folder, or whose `compactAt` is not below the `contextWindow` of the model it runs, an unknown one included, or that keeps a standing session in a folder that is not an existing directory, lists a `problem`. A file that is not a valid profile lists only its `id` and `problem`. The service reads the folder at each request.
22. The router chooses every model in code. The owner's `model` comes first (route `owner`). Otherwise the profile's model, as written (route `profile`), when the service runs it. Otherwise the same model id under a provider that serves the profile's provider on a subscription, from a fixed table: `openai` to `openai-codex` (route `profile-alias`). A review the service starts runs the reviewer model of rule 46 instead (route `cross-review`). A thread's worker runs the worker model of rule 47 (route `worker-asked`, `worker`, `worker-team` or `worker-default`).
23. A session started from a profile carries its `profile`. Every session carries the `route` that chose its model; one created before profiles carries `owner`, and so does one whose model the owner changed (rule 7e). A retry of a create whose session was made but not recorded records the session as it was made, not as a new routing would choose (rule 5).
23a. A thread's worker's session (rule 47) carries `startedBy`, the id of the thread's specialist session, the one whose `team_worker` call started it, in `GET /v1/sessions`, in `GET /v1/sessions/{id}` and in its `session` events, read with the session: the worker's session and its thread's naming of it commit together, so no copy of the session lacks it. Every other session leaves `startedBy` out.

**Threads and asks** ([ADR-0014](../adr/0014-delegate-in-threads-with-team-tools-in-code.md))

24. A thread is a piece of work a supervisor's session delegated to a specialist with `team_delegate`. Its `state` is `starting` while the service sets it up (with its `session` set once the specialist's session exists), `open` once the specialist has its brief, `done` or `blocked` after a report says so, and `closed`. A thread that could not start is `closed`, with why in its `report`, at most 2,000 characters. A thread names the `plan` it works for and the plan's task it delivers, `planTask`; a plan's own thread has a `plan` and no `planTask` (rule 48). A thread names `follows`, the thread its delegation carries on, and `successor`, the newest thread that carries it on, each left out for none (rule 26). A `closed` thread goes back to `open` once a message the service follows is in its specialist's transcript: the owner's (rule 10), or a supervisor's kept while it was closed (rule 30a) ([ADR-0061](../adr/0061-reopen-a-closed-thread-when-a-message-reaches-its-specialist.md)). The step that notes the message reopens the thread, once, with its `thread` event; one withdrawn, or one the durable store does not have, reopens nothing. A report, a close, the owner's stop of a shift and the delivery passes note the thread's placed messages first, so a message placed before a close reopens nothing after it, and a report filed after the message is taken. A reopened thread keeps its last `report`, carries `reopens`, how many times it reopened, and `reopenedAt`, when it last did, and takes its place on the desk again, over the cap if need be; its shift stays ended, and its worker is its own again (rule 47): no message reopens the thread before the stop its close owes the worker is done, and that worker's runs of the closed time reply to no one; a report its specialist files meanwhile is told to call again. A client orders copies of a thread by `reopens` first, then by closure within one lifetime, then by `updatedAt`, but takes the first list it fetches after a `resync` as it comes: a restored work database may have fewer `reopens`. `team_delegate`'s desk cap is checked again in the transaction that records the thread, since a reopen may have taken the last place. A plan's thread never reopens. A close's copy of a thread with fewer `reopens` than another is of an earlier lifetime: a client keeps the later one. A reopen publishes the thread's pull requests with it (`pull` events): `GET /v1/pulls` leaves out a closed thread's that are not open, so a client may have no copy of them.
25. The team tools go by role, in code. A session started from a `supervisor` profile gets `team_delegate`, `team_close`, `team_schedule` (rule 57), `team_send` (rule 30a), `team_gather` and `team_board` (rule 58), `team_launch` (rule 59), and `team_inbox` (rule 25a), with its other tools; a thread's specialist session gets `team_message` and `team_worker` (rule 47), and a plan thread's specialist session `team_message`, `team_plan` and `team_github` (rule 58) instead, with `read` as its only coding tool, when its profile allows it (rule 49); a worker's session gets no team tool; a review thread's session (rule 46) gets `team_diff`, `team_verdict` and `team_github` (rule 58, [ADR-0057](../adr/0057-let-a-cross-review-read-github-with-get-calls-for-what-a-pin-bump-brings-in.md)), with `read` if its profile has it, and no shell; a consult's session gets exactly `read`, when its profile allows it, `team_finding` and `team_github`, and no other tool (rule 52); a gather's proposal session gets exactly `read`, when its profile allows it, `team_propose` and `team_github`, and no other tool (rule 58); no other session gets one of these. A session started from a `private` profile gets none of them, whatever its role, `team_memory` included, and a supervisor's later tools never reach its older session ([ADR-0042](../adr/0042-give-a-private-agent-its-own-preamble-and-no-team-in-its-sessions.md)). At its start the service gives `team_verdict` to the session of each review thread not closed, and so does a review's start that finds its session made by an earlier run, before the brief; neither changes another tool. At its start the service also gives `team_github` to the lead's session of each plan thread not closed that has `team_plan` and lacks it, and to the session of each review thread not closed that has `team_diff` and lacks it, in the place a new lead or review has it, and changes no other tool (rule 58); a review's start that finds its session made by an earlier run gives it too, before the brief. Every session started from a profile but a consult's and a gather's proposal session gets `team_memory` (rule 32). Each tool refuses a caller of another role, too. Every team tool refuses a session whose profile is `private` as the profile is now, before it runs, with one error, also in a session that lists the tool from before. A call is one tool task: its steps are keyed by the session, the task and the call's id, so a run of the task again after a restart finds what it did, and a later call that reuses an id is a call of its own. The `question` tool is no team tool (rule 60): a session started from a `supervisor` or a `private` profile gets it after its other tools, a private one with no team tool, but not a thread's specialist session, a review's, a worker's, a consult's or a gather's proposal session. The `schedule` tool is no team tool either, and the one tool beside `question` a private profile's session gets ([ADR-0060](../adr/0060-give-a-private-agent-a-schedule-tool-of-its-own-checked-in-code.md)): a session started from a `private` profile gets it after `question`, but not a thread's specialist session, a review's, a worker's, a consult's or a gather's proposal session, and a session of any other profile, a `supervisor`'s included, gets no `schedule`. No team tool's refusal of a private profile runs before it; it refuses, before it keeps anything, a session whose profile, as it is now, is neither `private` nor a `supervisor`'s, or that works as one of those roles (rule 57).
25a. `team_inbox` lists, from the service's records alone, what waits for the owner and what was settled in the last 7 days ([ADR-0046](../adr/0046-let-the-supervisor-read-the-owners-inbox-from-pocketds-records-in-code.md)). It takes no arguments, reads GitHub not at all, and writes nothing. Its caller is a session whose profile is a `supervisor` as the profile is now; any other is refused. Its answer is text: what waits, as a client's Inbox counts it from `GET /v1/asks`, `/v1/pulls`, `/v1/plans`, `/v1/lessons` and `/v1/approvals` (each open ask with its thread, asking agent, question and age; each open pull request that is no draft, with its thread, title, `ready-for-human`, the verdict at its head, its CI and when the service last read it; each plan in review with its revision's graph and an empty gate; each lesson that waits; each pending approval; and, from `GET /v1/sessions`, each session whose question waits (rule 60), by the session's id and profile and when it is skipped, never by the question's words), then the asks answered or withdrawn in the 7 days before the service's clock and the pull requests merged or closed whose record changed in them, newest first, all read in one transaction. An ask's times are the service's own; a merged or closed pull request's time is its record's last change (its `updatedAt`), which the answer names so, since the service keeps no time of the merge or close. Its first line says how often the service reads each open pull request again (rule 39). The answer is at most 24 KiB and 400 lines: a longer one keeps the same number of first items of every list, the most that fit, and says so. A supervisor's session started before the tool gets it at the service's start, but a standing one, which takes it with its profile when idle (rule 7c).
26. `team_delegate` refuses, the desk's cap checked last: a caller that is not a supervisor; a target that is unknown, private, a supervisor, or cannot start (rule 7b); a repository the target's profile does not name, and no repository for a target with no home or workspace; a task that is empty or over 6,000 characters, or a title over 120; a `worker` that names no entry of the owner's worker list (rule 47), by its provider or its whole `provider/id` under the router's aliases, or one on a plan's start, whose lead has no worker, the refusal naming the list's entries; a `follows` that names no thread, a review thread (rule 46), or a thread a session of another profile delegated, as `team_close` refuses one, and a `follows` on plan work; and a full desk, where the desk is the threads not `closed` and its cap is `-desk-cap` (else `POCKETD_DESK_CAP`), 12 by default; a cap that is set but empty, not a number, or below 1, in the flag or the environment, stops `pocketd serve`. Otherwise:
   - The specialist's new session starts only from a profile that still passes the target rules when it starts, also after a restart, read again once its worktree is made. A session made already is finished without its profile; if its brief has not gone, its worktree is checked again as it is now, from the checkout its name was made from. The target rules check privacy and role before startability, which may look at the profile's folders.
   - With a repository, the specialist works in a git worktree at `<checkout>--<agent>-<slug>` on the branch `<agent>/<slug>`, new from the tip of `origin`'s default branch, or on that branch when git lists it already (a lookup that could not tell makes nothing) ([ADR-0056](../adr/0056-start-a-new-worktrees-branch-from-a-fresh-fetch-of-the-remotes-default-branch.md)). A new branch's base is fetched first, in the sandbox, within 2 minutes inside the call's deadline (`worktree.FetchTimeout`): `git ls-remote --symref origin HEAD` names the default branch, which must be a branch name, `git fetch --no-tags --no-write-fetch-head origin +refs/heads/<default>:refs/remotes/origin/<default>` fetches it, and the branch starts at the fetched commit's full id, so it tracks no upstream. When the lookup or the fetch fails and the call's deadline holds, the branch starts at the checkout's `HEAD`, and the brief carries one line that names the reason (`team.StaleBase`, the reason on one line of at most 300 bytes); a call whose deadline ended makes nothing. A folder or a branch that is there already is finished as it is, with no fetch; `<slug>` is the title's letters and digits, then `-t<thread>-` and the thread's whole random owner (16 lowercase base32 characters), so no two threads, of any data folder, share a name, and a folder or branch of the name is one an earlier try of the same thread made. The checkout must be the top of its repository. Every worktree the specialist gets is checked, also a new one after the checkout's hooks ran, with its checkout checked again as the top of its repository: a folder at its path, not a link to one, of the repository, on its branch, which names a commit, registered by git at its own path (its git folder in the repository's registry, its backlink, absolute or relative, naming `.git` in the worktree's own folder (that folder, as written, compared in the sandbox, never cleaned as a string, so a copy whose `.git` is a hard link is another folder), and its `.git` a file, not a link), and not locked, with the lock file of that worktree's git folder. Every path is looked at and compared by a command in the sandbox, bound by the call's deadline, never by the service itself. A locked one, as git leaves one a stopped try did not finish, is refused; the service never removes one. The sandbox's checks (git, existence, a short read, and the folder a session's new worktree makes alone, rule 6a) get a tool command's environment (rule 14c), and one whose sandbox fails is an error, never an answer: a check that could not run (a probe that failed, git that did not start, a deadline that passed) says so with its cause (git's exit status comes back apart from the sandbox's, so a sandbox that failed around git, a shell that could not start git, or a signal that ended git, is never git's answer), never that the worktree is wrong, and a worktree that is wrong says so with git's word for it. git runs in the sandbox (rule 14e), the service keeps at most 4 KiB of its errors, output past 64 KiB is an error, never a cut answer, and it ends with the call's abort or after 5 minutes. Without a repository, the specialist works in its profile's `home`, else its `workspace`, which must be a folder as a command in the sandbox sees it.
   - The specialist's session starts from its profile with the router's model, titled `T<thread> · <title>`, keyed by the thread's random owner, and only while the thread, read again, is not closed, the call is not aborted, and the profile and the models, read again last, after the worktree's check and right before the session starts, still passes the target rules with the same folder; the worktree is checked again then too (of its repository, on its branch, not locked, with a git deadline of 30 seconds), and a home must still be a folder. The session and its thread's attachment commit together, before either is published, and the session is watched before its brief goes, so the brief's entry reaches the event stream. The thread takes the session, the specialist gets the brief, which the service writes, and the thread opens, in one step that no close falls within. A closed thread never gets a brief, also when its call runs again. A thread whose brief went, or may have gone (its submission found by key, or not known), never closes because a later step failed: it stays `starting`, and its first report moves it on, or a delivery pass opens it once its delegating call's task ended, without the brief again. A session an earlier run made, whose brief has not gone, has its folder checked as it is now before the brief goes: a worktree as a new one's, a home as a folder. A thread still `starting` whose delegating call's task has ended will not start: a delivery pass closes it, after a restart too, unless its specialist may have its brief. The brief is kept with the thread and counts as delivered only once its entry is in the specialist's transcript: one an abort withdrew is sent again, once its specialist's folder is checked again as it is now (an abort of the call that sends it stops the check): a folder no longer as the brief names it gets no brief, and its thread, starting or open, closes with why; a check that could not tell sends nothing and is tried again. A known limit: the sandbox's shell cannot tell a lookup that failed (an I/O error) from an entry that is not there, so a home that such an error hides reads as gone. An aborted call starts no session, or sends no brief (its first submission takes the call's context), and closes the thread; a call the service's stop cut off leaves the thread starting, and finishes when it runs again.
   - A supervisor's session names, in its instructions, the agents it can delegate to now (those the target rules accept, with somewhere to work) and the desk's cap, and the owner's worker list, or why it cannot be read, with when to pass `worker`.
   - A `follows` names the thread the new one carries on, in any state ([ADR-0061](../adr/0061-reopen-a-closed-thread-when-a-message-reaches-its-specialist.md)): the new thread records it, and the followed thread takes the new one as its `successor` in the same step, with its `thread` event; the newest one wins, and a delegation run again names nothing again. A refusal on a `closed` thread names the first of its successors that is not `closed`, following at most 16.
   - A `worker` resolves to its first entry of the owner's list when the thread is recorded, and the thread keeps that model: its worker runs it (rule 47), whatever the list or the profile says later ([ADR-0022](../adr/0022-run-any-session-on-any-sign-in-and-choose-workers-from-the-owners-list.md)). A plan task's delivery (rule 50) takes it too.
27. `team_message` files a report on the caller's thread: a `status` of `working`, `done` or `blocked`; a `message` of at most 6,000 characters; and at most 4 asks, each a `question` of at most 500 characters with no `options` or 2 to 6 distinct ones of at most 40 characters. The report and its asks are filed in one transaction, once per call: the thread takes the status's state (`working` keeps it `open`) and the message as its `report`, and a run of the call again never writes over a newer report. The supervisor's session gets the message `[T<thread> · <agent name> · <status>] <message>`, followed by the ids of the asks. An ask whose question is an `open` ask's of the same thread, once each has its words joined by single spaces, its ends trimmed and its case lowered, files no new ask: the report names that open ask in its place, among the ids, and the specialist is told it waited already and no new ask was filed; an answered or withdrawn ask is not matched, and a run of the call again names the same asks ([ADR-0055](../adr/0055-file-a-repeated-ask-as-the-threads-open-one.md)). A plan thread's report takes no `pull_requests` (rule 49). The message is kept with the report, and sending it is the service's: it counts as sent only once its entry is in the supervisor's transcript, a thread's reports go in the order they were filed to each session, whatever another session takes (rule 47), one that cannot go now is tried again every second until it goes, and at the next start, and the specialist is told the report is filed. A closed thread takes no report, and keeps none of its asks; its refusal says what the specialist can do instead: the thread that carries its work on (rule 26), its plan, which settled it, or the owner, whose message reopens it (rule 24). A report that names a pull request another thread links keeps nothing, is refused before the pull request is read on GitHub, and says to report again without it.
28. Closing a thread first withdraws every attempt of its brief that is still queued, so a closed thread's specialist never starts its work; a close whose withdrawal fails does not happen (`internal`), and a retry closes it. The close reserves its request id before any withdrawal, so a close refused for its request id touches no queue; a close that fails with no withdrawal taken effect frees it, and a `team_close` reserved and cut off before it committed finishes when its call runs again. `team_close` closes a thread that a session of the caller's own profile delegated, recorded with the call's key: the call run again answers as the first did, with a text that depends only on the thread. The owner closes any thread with `POST /v1/threads/{id}/close`; closing a closed thread changes nothing, but that it notes the thread's messages already in its specialist's transcript first, and closes the thread one of them reopened. A close drops the thread's worker's messages, its shift's and its supervisor's that are not placed in the transaction that closes it; a close of a closed thread drops none.
28a. A closed thread's worktree is removed by the service, which writes nothing on GitHub for it ([ADR-0054](../adr/0054-remove-a-closed-threads-worktree-in-code-with-no-github-write.md)). Every close the service publishes queues the thread, of a repository, and a review pass tries it at its end, outside the team's locks, once the thread's specialist's and worker's sessions are idle; a check that could not tell is tried at the next pass. It takes only the thread's own folder, whose name ends with `-t<thread>-<owner>`, never an owner's session worktree (rule 6a). The folder must be a worktree git registered, not the checkout, and not locked; a task's HEAD on its branch, a review's detached at the head it reviewed; `git status --porcelain` empty, and no index entry marked assume-unchanged or skip-worktree (`git ls-files -v` tags every entry `H`), since status and `git worktree remove` cannot see a change to such a file; and a task's HEAD the recorded head of one of its linked pull requests or an ancestor of one, or, with none linked, an ancestor of its branch's start (the oldest entry of the branch's reflog). Then `git worktree remove` without `--force`, and a task's branch with `git branch -d`, never `-D`; a branch git keeps stays. A folder the service keeps gets one line in the thread's report, `pocketd kept the worktree <path>: <reason>.`, once a run, and no Inbox item; a write of that line that fails is tried at the next pass, and the thread is decided only once it is written. A closed thread keeps its worktree while a message that may reopen it is on its way (rule 24): an owner's message the service follows, or a supervisor's kept while the thread was closed and not noted. A removal and a message to the closed thread's specialist go one at a time per thread, from the look at the thread to git's end and from the look at its folder to the record of the message. A thread that reopened is queued again at its next close ([ADR-0061](../adr/0061-reopen-a-closed-thread-when-a-message-reaches-its-specialist.md)).
29. `AnswerAsk.answer` is 1 to 2,000 characters once trimmed (`proto.MaxAnswer`); the options are suggestions, and any answer is taken. An ask is answered once: answering it again with a new `requestId` is `conflict`, and so is answering one a supervisor's message withdrew (rule 30a), whose message says so and that the answer was not sent; such a refusal spends no `requestId`. The answer reaches the asking session as the message `The owner answered A<id> ("<question>"): <answer>`, once. It is keyed by the ask's own key and a digest of the answer, never the ask's number, and counts as delivered only once the durable store's record of its key shows its entry in the transcript: a busy session's queue holds it; one an idle session holds after a failed run (PiG keeps such a queue until the next input) is withdrawn while still queued and sent again as a new input, whose run starts from its own entry; and one an abort withdrew, or the durable store does not have, is sent again under a key of its own, unless an earlier attempt still lives. One message is placed at a time, so no two callers send it twice, and a brief is sent again only under a fresh read of its thread that finds it not closed. A thread's brief whose fate the durable store cannot tell is neither sent nor its thread closed until it can. pocketd's stop ends the delivery passes before the engine closes. Sending it is the service's: an answer that cannot go now still answers 200, and the service tries again every second until it goes, and at its next start, after the tasks resume. At its start, off the start's path, it sends what a stop left unsent and stops each closed thread's worker; a stop that fails is tried again. A message to a worker's session is refused with `409 conflict`. A thread's close stops its worker's run. A model whose provider's stored sign-in is an API key runs any session, as a subscription's does (rules 14d and 22). `pocketd login` keeps a key only for a provider of its list, `deepseek` today, which has no OAuth sign-in, or for an owner's provider whose `key` is true, refusing one whose `key` is false ([ADR-0023](../adr/0023-add-the-owners-own-model-providers-from-a-file-checked-in-code.md)), and only while no service serves the data folder; `pocketd login` keeps only a key of printable ASCII with no space, no `$` and no `!` first, which PiG would read as an environment variable or a command, reads it, one line checked as typed, from a terminal without showing it, or at most 1026 bytes of it from a pipe, restoring the terminal when interrupted, and stores exactly that: it never runs the provider's own key flow.

**Plans and consults** ([ADR-0020](../adr/0020-plan-before-building-with-the-plan-gate-and-consults-in-code.md))

48. A plan is a piece of work its lead plans before the team builds it. A supervisor's `team_delegate` says, in its description, how to start a plan and deliver its tasks, and that plan work names its plan. The supervisor starts one with `team_delegate` and `plan: {"start": true}`, naming the lead as `agent` and the idea as `task`; `plan` is either that, or `{"id", "task"}` (rule 50), never both. The service refuses a start by a caller that is not a supervisor; of a lead the target rules of rule 26 refuse, or with no `home` or `workspace`; with a `repository`; with a task that is empty or over 6,000 characters, or a title over 120; and while 3 plans are open, counted in the transaction that records it. Otherwise it records the plan and its plan thread together, and the thread starts as rule 26 says, in the lead's `home`, else its `workspace`, with a brief the service writes. The plan thread takes no place on the desk: rule 26's cap counts the threads not `closed` but plan threads. A plan's `state` is `drafting`, `review` (it waits for the owner's approval), `approved`, `building` (a task was delivered), `done`, or `dropped` (its thread closed before it was done). Closing the plan thread, by the owner, `team_close` or a start that failed, drops a plan not done, and stops its consults (rule 52).
49. `team_plan` takes an `action`: `read`, `write`, `tasks`, `ready` or `consult`, each with only its own fields. Its caller is the plan thread's specialist session, found by the calling session, never by an argument. A plan's lead has no worker: `team_worker` refuses it, since it builds nothing. It reads GitHub with `team_github` (rule 58). A change is recorded with the call's key in the transaction that makes it: run again, the call answers as it did and changes nothing. A call stopped before its change was recorded, also while it waited for the locks that order thread and ask changes, records nothing.
   - `read` shows the plan's state and gate, its text and `rev`, its graph with each task's acceptance lines, its asks and its consults, and the agents a task can go to or a consult can ask, with their repositories and whether they have a home. It answers in pages (`page`, from 1) of at most 16 KiB and 400 lines, each naming its rev, the read's `snapshot` and whether a page follows: no tool result is cut. A page past the first names the snapshot of its page 1, and a read that changed since is refused, to be read again from page 1. Each consult shows its question and the ask it is on.
   - `write` replaces the plan's `text`, 1 to 20,000 characters, from the `rev` it was written from: the text's SHA-256 in hex, and none for the first write. A `rev` that is not the plan's now, and a text that is the plan's as it is, are refused. `asks` names the plan thread's answered asks the write puts in; an open ask, or one of another thread, is refused. A named ask is `written`.
   - `tasks` drafts the graph, version 1 and up, for the plan's current `rev`, and supersedes a draft. A graph has 1 to 30 tasks with unique ids `t1` to `t999`; each has a title of 1 to 120 characters, 1 to 8 `acceptance` lines of at most 300 characters each, an `agent` the target rules of rule 26 take (privacy and role) with a `repository` of its profile, or none for its `home` or `workspace`, and `deps` that name other tasks of the graph, with no cycle. A plan with no text takes no graph.
   - `write` and `tasks` are taken in `drafting` and `review`, and take a plan in `review` back to `drafting`; `consult` only in `drafting`; none once the plan is approved.
   - The plan's asks are its thread's: the lead asks with `team_message`. A report with an ask takes a plan in `review` back to `drafting`, in the transaction that files it. A plan thread's report takes no `pull_requests`. While the plan is `drafting` or `review`, the answer's message (rule 29) ends with `Write it into the plan with team_plan write, naming <id> in asks.`
50. The plan's gate is what it waits for: each open ask of its thread (`A<id> open`), each answered one no write named (`A<id> not written`), never a withdrawn one (rule 30a), and each consult `starting` or `running` (`K<id> starting`); once approved, only its open asks; once ended, nothing. A plan is settled when its gate is empty.
   - `ready` moves a settled plan in `drafting`, with text and a graph drafted for its current `rev`, to `review`.
   - `ApprovePlan` names the `rev` and the graph `version` the owner saw: a `rev` of 64 characters and a positive `graph`, else `bad_request`. It approves a plan in `review`, settled, at that `rev`, with that version as its draft graph; otherwise it is `conflict`, and the message says why. The request id is claimed in the transaction that approves (rule 5): a retry answers with the plan as it is, and the same id for another plan is `conflict`. The approval makes the graph approved and its tasks with no dependency `ready`, and records the device's name as `approvedBy`.
   - `team_delegate` with `plan: {"id", "task"}` delivers a task: its call must pass rule 26's rules, the desk's cap included, and come from a session of the profile that started the plan. In the transaction that records its thread, the plan must be `approved` or `building` with no open ask, and the task in its approved graph, `ready`, for the call's `agent` and `repository`; otherwise nothing is recorded, and the refusal names what waits. The task is then `delegated` to the thread, and the plan `building`. The thread's task is the supervisor's text, then the task as approved: its id, the plan, the `rev`, its title and its acceptance lines, then the plan's text at that `rev`. It asks for one pull request only of a task on a repository; a task with no repository is told it opens none; its title, when the call gives none, `P<plan> <task> · <task title>`. Both come from the plan as the transaction that checks the gate reads it. The same call run again finds the same thread.
51. A task is `waiting` while a dependency is not `done`, and `ready` once every one is; `delegated` while its newest delivery's thread works; and `done` once that thread closes with its work done: one of its linked pull requests `merged` and none `open`, or, with none linked, its state `done` when it closed. This is decided in the transaction that closes the thread, whichever path closes it (the owner, `team_close`, rule 39's round, a start that failed); the tasks it frees become `ready`. Before the owner's close or `team_close` (one cut off and finished later too) settles a task of a live plan, its pull requests that have not merged are read again on GitHub, their state alone, never their label; one that cannot be read refuses the close, which is tried again, and the close commits only while every one not merged that the thread links then was among those read. The owner's close checks its `requestId` before any of this, and an aborted `team_close` stops its reads and closes nothing, as does one stopped while it waited for those locks, before it claimed its request id. `team_close` of a plan's own thread says it dropped a plan not done and freed no place on the desk. A delivery the desk's cap refused holds its plan, counted again where the hold is recorded, together with the gate: a task the gate would refuse gets that refusal and holds nothing, a place freed since the count is the delivery's, and a hold that cannot be recorded is an error to try again. The next close of any thread on the desk, a task's that failed to start included, tells that plan's supervisor its ready tasks, once, and a delivery pass runs at every close. A thread that closes otherwise makes its task `ready` again. The close of an older delivery's thread, or of a task of a plan that ended, changes nothing. When every task is `done`, the plan is `done`, and its thread closes in the same transaction, with the report `Closed: every task of plan P<id> is done.` A known limit: a task whose thread closed before its pull request merged is `ready` again, and that merge later does not make it `done`.
52. `team_plan consult` asks 1 to 3 distinct `agents` a `question` of 1 to 2,000 characters, on one of the plan's asks (`ask`) or none. An expert is not the lead, passes the target rules of rule 26, startability included, and has a `home` or a `workspace`. At most 3 consults of a plan start or run at once, and 8 in all; a call past either is refused whole.
   - Each consult is a session the service starts from the expert's profile, in its `home`, else its `workspace` (a folder as rule 26 checks one), with the router's model, keyed by the consult's random owner, and titled `K<consult> · consult on P<plan>`. It gets exactly `read`, when its profile allows it, `team_finding` and `team_github` (rule 58). Its first message is the question, which the service writes in the transaction that records the consult's session, with the plan's text, as written, and its `rev`, from the plan row and the ask it is on as that transaction reads them, or that the plan has no text yet: the expert's `read` cannot reach the plan.
   - `team_finding` files the consult's one finding: a `stance` of `supports`, `objects` or `neutral`, and a `summary` of 1 to 2,000 characters. It is refused from any session but a running consult's, a second time, past the consult's 60 minutes (by the service's clock, whether or not a pass ended it), and when the plan is no longer `drafting` or `review`. `team_memory` refuses a consult's session too. It is recorded with the call's key: run again, it answers as it did.
   - A consult's new session starts from the expert's profile as it is under the locks that order thread and ask changes, checked again there, with its folder checked again there as a folder; a session an earlier run made keeps the profile it was made from. A read of the expert's profile that failed, rather than a profile that is gone or invalid, fails nothing: the consult starts at a later pass, before its deadline. No fresh session starts past the consult's deadline, checked again right before it would. The question goes only once the session is watched, and never past the consult's deadline, checked again right before its submission. Each pass arms a timer at the earliest deadline of the consults it read. A consult that fails to end holds back no other consult's start.
   - A consult with no finding 60 minutes after its call fails, as does one whose expert no longer passes these rules when it starts. One whose plan ended is `stopped`. A consult's question still queued is withdrawn before the consult ends, and one not placed by then is never sent; a consult whose withdrawal fails ends at a later pass.
53. The service owes these messages, each a note filed in the transaction of the change that causes it, keyed by the plan thread's or the consult's random owner, placed once as rule 29 places a message, and oldest first to each session:
   - to the session that started the plan, naming each task to deliver with its title, its agent and its repository (or none): `[P<id> · approved] …` at the approval, for the ready tasks; `[P<id> · <task> done] …` when a task's done readies others, naming them; `[P<id> · <task> ready again] …` when a task's thread closed without its work done, while it started too; `[P<id> · A<ask> answered] …` when the owner's answer clears the last open ask of an approved plan with ready tasks; `[P<id> · a place on the desk is free] …` when a thread on the desk closes after the cap refused a ready task of the plan (rule 51); and `[P<id> · done] …` when the plan is done;
   - to the consult's session: its question;
   - to the lead: `[K<id> · <agent name> · consult on P<plan>…] <stance>: <summary>` for a finding, and `… It ended without a finding: <why>.` for a consult that failed.

   While an open ask holds an approved plan's gate, a task's close files no delivery note: the answer that clears it names every ready task. No other message tells the same: the supervisor is not told that a plan waits for the owner, and the lead is not told of the approval. A delivery pass runs when a note is filed, and at the deadline of each consult that starts or runs.
54. `GET /v1/plans` lists every plan, the most recently changed first, each with its `text`, its `rev`, its gate as `waiting`, its newest graph with its tasks' `state` and `thread`, and its consults with their findings, as one transaction read them. Plan events go out with the change that made them, under the lock that orders thread and ask events: a plan's start, a write, a draft, `ready`, a report or an answer on its thread, a consult's start, finding or end, the approval, a task's delivery, and each close of one of its threads. An ask filed or answered on its thread moves its `updatedAt`, as each of these changes does. A change publishes the plan as its transaction read it where it can, and a report once, whatever its asks; a plan whose read after a change fails goes out at the next delivery pass.

**Shifts** ([ADR-0024](../adr/0024-run-a-delegated-thread-in-rounds-as-a-shift-driven-in-code.md))

55. A delegation may run its thread as a shift: `team_delegate`'s `shift` takes `stop`, the completion condition, 1 to 3,000 characters; `max_rounds`, 1 to 100, 20 when left out; `hours`, the deadline after the thread is recorded, above 0 and at most 24, none when left out; and `ci`. The tool's text says to name green CI in `stop` only with `ci` true: without it nothing waits for CI, and a proposal's `stop_when` says the same (rule 58). A limit given is a limit: `max_rounds` or `hours` given as 0 breaks the rule. A shift that breaks a rule, or one with `plan`, refuses the delegation. The thread and its shift are recorded in one transaction; the shift runs at round 1, which the brief begins, and the brief says its rules. A shift's brief, too, is submitted only to an idle specialist. A brief not in the specialist's transcript by the deadline, or a thread still starting then, is never submitted, the deadline being the last check before each submission, and one still queued is withdrawn by a pass the deadline wakes: the thread closes, the shift ends (`deadline`), and the supervisor gets a note, `[T<id> · shift] The shift ended before it began: …`. The service drives it in code, after each run of the specialist or its worker that ends, after a round's message or a shift's brief is noted placed, after each round of pull requests, and at its start, one pass at a time:
   - A round ends once the message that began it (the brief, a round's, or the summary's) is in the specialist's transcript, found by its request key in the durable store, the specialist and its worker are idle, and nothing is owed to either, whatever thread filed it: no message the service sends (a cross-review's verdict included), no reply of the worker's run that ended, and no answer to an ask of the specialist's that has not reached it. A decision is committed only while the round is still as it was read, and only in a transaction that finds nothing owed to either. Its answer is the model's last text after that message; its verdict, the answer's last line `STATUS: DONE`, `STATUS: CONTINUE` or `STATUS: BLOCKED[: reason]`, read in code, from the round's last run's final response alone, after its own input, one the model ended (stop reason `stop`): a last run that failed with no such response fails the round, whatever an earlier run said, and text beside a tool call, or cut short by an abort or a failure, is no verdict; no such line is `none`, which goes on as continue. Each round's verdict is recorded with the round.
   - `BLOCKED` stops the shift (`blocked`). `DONE` stops it (`done`), and with `ci`, only once each pull request the thread links that is not closed has CI green at its head, read on GitHub first, with at least one: a pull request that cannot be read, or CI that runs, leaves the round for a later pass, until the deadline (`deadline`); one that fails, or a pull request with no checks, or none linked, sends the next round naming what fails, and the same failing checks in three `DONE` rounds in a row stop the shift (`failed-check`): any other round ends the streak. Each linked pull request is read from GitHub's answer alone, one recorded closed included, and only one GitHub says is closed is skipped; each CI read is bounded, and green counts only while each pull request, one closed included, is still as it was read; every page of checks and statuses is read, and a total that moves, or a check that repeats, between pages is never green, nor is a list of more than a page with a check run that has no id. A round that waited on CI to its deadline stops there with no read more, and a read of CI ends at the deadline. A done checked green pins those pull requests at those heads: no report of its summary round links another. A round that waits on CI reads it at most once every two minutes, whatever else runs a pass, and wakes a pass of its own then, or at the deadline if that is sooner. A pull request GitHub names with another id than the one linked fails the check. Before each next round, the round limit (`max-rounds`) and the deadline (`deadline`) stop it. A run that ended failing with no answer ends it (`failed`), its round recorded with no verdict, which ends the CI failure streak.
   - Each round after the first is one message, `[shift] T<id> · Round <n> of <max> …`, kept in the outbox in the transaction that moves the round's count, and placed once, submitted only while the specialist has no run and nothing waiting in its inbox, by a submission PiG refuses while the session has a run, so it never waits in PiG's queue, and only while it begins the round under way: one of a round that ended, or of a shift paused or ended, goes to no one, and one still queued is withdrawn before a stop, a pause or a close commits. One not in the transcript by the deadline is never submitted again, the deadline being the last check before each submission, and the shift stops for its deadline. A shift that stops gets one summary round, its message kept with the stop, which asks for one `team_message` with status `done` (for `done`) or `blocked`, with each new decision as an ask, and names the thread's asks read in the transaction that keeps it: those still `open`, by number and question, which it says not to file again, and those answered since the shift began, by number, question and answer, which it says to act on; each list names the first 8 with their text, a question cut to 200 characters and an answer to 300, the next 100 by number, then a count ([ADR-0055](../adr/0055-file-a-repeated-ask-as-the-threads-open-one.md)); that report is refused with another status, before the summary's message is in the specialist's transcript, or once the shift has left the summary round it was checked in, as is any report checked in that round, and the run that filed it files no other report, also after a resume, and ends the shift in the transaction that files it. A summary round that ends with none gets the service's report, `The shift ended: <why>. It took <n> of <max> rounds.`, filed once in the transaction that ends the shift. Until the summary round, `team_message` with status `done` or `blocked` is refused; a `working` report goes as any.
   - The owner's message to the specialist's session pauses a running shift (`person`) as its `requestId` is claimed, before the message goes: the same `requestId` again pauses nothing, and a message that fails leaves the shift paused, keeping its `requestId`, so it pauses nothing when tried again; the service's own messages never do, nor does a supervisor's (rule 30a), which the round waits for, as for anything owed to the specialist, and whose run's `STATUS` line is the round's when it is the last. `POST /v1/threads/{id}/shift/stop` ends a shift that is not ended (`stopped`) and files the service's report in one transaction; the shift's own message still queued is withdrawn first, and the service sends no more rounds. The stop ends the shift only: the specialist's and its worker's runs go on to their ends, what the service owes them still goes, and a report they file goes as any; the owner stops a session with its abort. A stop of a shift that ended answers with the thread as it is, and its `requestId` is spent all the same. `POST /v1/threads/{id}/shift/resume` goes on with a paused shift, or one that ended for a reason other than `done` or `closed`, while rounds and time are left, at its next round, keeping its failure count, else `409 conflict`, as it is while the specialist has no run and an input waiting in its inbox, read under the shift's lock. Each takes a `requestId`, claimed in the transaction that changes the shift: the same one again changes nothing, checks nothing again, and answers with the thread as it is. A thread with no shift is `404 not_found`; one whose specialist does not have its brief yet is `409 conflict`. A thread's close ends its shift (`closed`) in the transaction that closes it, with a note to the supervisor, `[T<id> · shift] The shift ended: its thread closed. …`, for a shift not ended yet; its shift messages still queued are dropped.
   - A thread carries its shift: `stop`, `maxRounds`, `deadline`, `ci`, `state` (`running`, `summary`, `paused` or `ended`), `reason`, `why`, `round`, `failures`, its `rounds` (`n`, `verdict`, `reason`, `at`) and `endedAt`, on `GET /v1/threads` and in the answers of `stop`, `resume` and a thread's close, read with the thread in one transaction, and in its events: an event whose shift cannot be read is held back and sent whole later, never with no shift. A shift's change moves its thread's `updatedAt`.

**Terminals** ([ADR-0025](../adr/0025-give-the-owner-a-shell-on-the-service-host-from-the-desktop.md))

56. A terminal is a login shell of the service user, started as `-<name>` from its shell in `/etc/passwd` (else `/bin/bash`), in a session of its own on a pseudo-terminal of the service host. The service runs it for any device signed in, outside the sandbox of rule 14e. It gets `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH`, `LANG`, `TZ`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS` and `LC_*` of the service's environment, and nothing else of it, `HOME` set to the user's home when the service has none, with `TERM=xterm-256color` and `COLORTERM=truecolor`. The service logs none of its keys or its output.
   - `StartTerminal` starts one in its `folder`: `home` (or none), the user's home; `session`, the folder of session `session` (`not_found` for none); or `path`, an absolute path to a folder that exists. Each takes only its own field. A folder the shell cannot enter, or one gone by the time it starts, gives the home folder, else `/`, and the terminal is listed in the folder it started in. `rows` are 2 to 500 and `cols` 2 to 1000, both 0 for 24 by 80. At most 4 shells run at once (`proto.MaxTerminals`), one that ended counting until its process is gone: another start is `conflict`, as is a start while the service stops. A terminal's `title` is its folder's name. A start's `requestId` is recorded with its terminal's id before the shell starts, and freed when no shell started, so a retry never runs a second login (rule 5).
   - The service keeps the last 256 KiB of a terminal's output (`proto.TerminalKept`), from a character's first byte, and counts every byte since its start. `GET /v1/terminals/{id}/output?from=<byte>&ack=<byte>&tab=<name>` answers its output from byte `from` to the end: from the first byte kept when `from` is older, from the end when it is past it. It answers at once when there is output past `from` or the terminal exited, else after 25 seconds with none, its `from` and `to` the same byte. With `wait=0` it answers at once with what is kept, none included: a client reads a terminal's history so, and what comes after it live. An answer that says `exited` carries the `exitCode` (128 and the signal for a shell a signal ended), and no output follows it.
   - `ack`, at most `from` and `from` when left out, is how much of the output the client drew; `tab`, 1 to 64 letters, digits and dashes, names the client, and may be left out. A terminal whose output runs more than 128 KiB past what its slowest client drew stops taking output, so its programs wait, until that client draws more: a `tab` counts for 30 seconds after its last poll, and a terminal keeps the 16 seen last; with none, the highest `from` asked for counts. A `from` or an `ack` past the end counts as the end.
   - `TerminalInput` carries a `tab`, a `seq` from 1, and `data`, at most 32 KiB (`proto.MaxTerminalInput`). An input whose `seq` is not above the last one its `tab` sent writes nothing, and answers 200: a client sends an input again, after a failure, with its `seq`. While 32 KiB of keys wait for the shell to read them, an input waits for room, as on a full pipe; one that finds none before its client gives up is not taken, and is sent again with its `seq`. A `tab` is kept for 10 minutes after its last input; a 17th while 16 are kept is `conflict`. `ResizeTerminal` takes `rows` and `cols` as `StartTerminal` does, neither 0. Both are `conflict` for a terminal whose shell exited, while its output still drains too.
   - A terminal ends on `DELETE /v1/terminals/{id}`; once no poll waits on it and its last poll began 60 seconds ago; 60 minutes after its last input; and when the service stops. The service checks the two spans every 5 seconds. Its process group gets `SIGHUP`, and `SIGKILL` 2 seconds later, and its pseudo-terminal closes 5 seconds later if it still runs. It leaves the list at once, and a call on it is `not_found`, a poll that waits on it included. Once its shell exited, the service reads its output until its pseudo-terminal ends, a second at most, then closes it, whatever still holds it open, as a job left in the background. A terminal that exits stays listed, `exited`, for 60 seconds. A `terminals` event carries the whole list after each change.

**Schedules** ([ADR-0030](../adr/0030-send-scheduled-messages-from-the-owners-file-and-the-supervisors-tool-in-code.md), [ADR-0060](../adr/0060-give-a-private-agent-a-schedule-tool-of-its-own-checked-in-code.md))

57. A schedule sends a session the message `[scheduled] <message>` later, or on repeat: the owner's, from their schedules file, a supervisor's own, from `team_schedule`, and a private agent's own, from `schedule` ([ADR-0060](../adr/0060-give-a-private-agent-a-schedule-tool-of-its-own-checked-in-code.md)).
   - The owner's schedules are `schedules.json` in the profile folder, read as rule 21 reads a profile: `{"schedules": [{"id", "when", "zone", "profile", "message"}, …]}`, every key as written, none named twice. A file that is not that object, or that the service cannot read, sends none of them, and the list says why (`problem`). An entry that breaks a rule sends nothing and lists its `problem`, and the others go; it keeps what the service recorded for its `id`, its one `id` key read whatever else breaks it: an `id` of 1 to 64 letters, digits, `.`, `-` and `_`, starting with a letter or a digit, the same in any case as no other entry's (two such entries both have a problem); a `when` this rule reads; a `zone` that is an IANA time zone (not Go's `Local`), or none; a `profile` that is a profile's id; exactly one action, a `message` of 1 to 4,000 characters once trimmed or a `gather` (rule 58); and no other field. An entry goes to its profile's standing session (rule 7c): a profile that is gone, invalid (a symbolic link included, rule 21) or not `standing` misses the time (`missed`, with why), and a profile the service cannot read now holds the time for a later pass. A standing session not made yet is made at the time, as the first `CreateSession` of rule 7c would make it, from the profile as it is right before it starts, under the profile's key, which is its request's key too, and recorded as the profile's standing session in the transaction that records it; one the profile cannot start misses the time, and says why ([ADR-0033](../adr/0033-gather-proposals-from-the-team-in-read-only-sessions-in-code.md)). A time goes only to a watched session: one whose watch the service cannot start holds the time for a later pass. A message filed for a standing session is submitted only once the session takes what its profile says now, as before the owner's message (rule 7c): while its profile cannot be applied, or the session is at work while its profile's change waits, the message waits, and a repeat skips its times meanwhile.
   - A supervisor's session (rule 25) keeps its own with `team_schedule`: `add` takes `when` and `message` and sends to the calling session; `list` shows the session's own that still go out and, for a standing session, the owner's that go to it, a gather with its skill, its agents and its note (rule 58), with how many times a repeat skipped and why its last skip did, as recorded then, in pages (`page`, from 1) of at most 16 KiB and 400 lines, each saying whether one follows, so no tool result is cut, an entry longer than a page in parts across pages; `cancel` takes one of the session's own, `S<n>` (one `S` or `s`, or none), which sends nothing more, and answers the same again; the owner's change only in their file. `add` is keyed as rule 25 says: run again, it answers as it did and adds none, whatever the rules say by then. **Search** ([ADR-0050](../adr/0050-search-every-session-through-an-fts5-index-in-the-work-database.md))

63. `GET /v1/search?q=<words>&limit=<n>` finds sessions by their titles and by what their transcripts say. It changes nothing.
   - **The words.** The service reads `q` as `proto.SearchWords` does: each run of letters, numbers, private-use characters and non-spacing marks is a word, in lower case, once, in the order given; every other character splits words. `q` has at most 200 bytes (`proto.MaxSearchQuery`), at most 8 words (`MaxSearchWords`) of at most 64 characters each (`MaxSearchWord`), and at least one word. `limit` is a whole number from 1 to 200 (`MaxSearchLimit`), 50 when absent (`DefaultSearchLimit`). A `q` or a `limit` that breaks this is `bad_request`.
   - **What it searches.** A session's `title`, and the entries of its transcript: a `user` entry's text, which holds the owner's message, a thread's brief, a report, an answer or a supervisor's message, and an `assistant` entry's text, then `Tools: ` and the names of its tool calls. No thinking, no tool's arguments or result, and no `system`, `compaction` or `reset` entry. An entry's first 32 KiB of text are searched.
   - **What matches.** A title or an entry matches when every word begins one of its words, whatever its case: `deploy` finds `Deployment`, not `redeploy`. Diacritics count: `cafe` does not find `café`.
   - **The answer** is `SearchResults`: `words`, the words read; `hits`, newest first; `cut`, set when a hit was left out; `indexing`, set while the service still reads older entries into its index, as on its first start with search, when a hit may be missing.
   - A hit names its `sessionId`, its `entryId` (none for a title's hit), its `field` (`title`, `user` or `assistant`), its `at` (the entry's time, absent when PiG gave the entry none; a title's hit, the session's `updatedAt`), and a `snippet` with its `marks`. Hits are ordered by `at`, the newer first, a title's before an entry's at one time, and the newer entry first.
   - At most `limit` hits, and at most 5 of one session's entries (`MaxSearchSessionHits`). The service chooses entries, newest first by `at`, from the 20,000 that match last written; `cut` is set when it left out a hit for any of these.
   - A `snippet` is the text around the first match: its whitespace runs as one space, at most 160 characters (`SearchSnippet`) from the start of a word at most 40 characters before the first match, cut after a word where it can, with `…` where the text goes on. `marks` are the matches in it, in order: each `{start, end}` a byte range of the snippet, the start of a word that a word searched begins. A snippet with no match the service can mark shows the text's start, with no marks.
   - An entry reaches the index after its `entry` event, within seconds. The service reads each session's entries from PiG's records after the newest one it indexed, so an entry whose event was lost, or written while it stopped, is found too.

   - A usage's tokens are its `total`, or its parts summed when they are more. A sum of usages, a day's and a session's alike, counts as its `total` each one's tokens.

A subscription, signed in by OAuth, is paid by the month: every `usage` the service sends of its models, a session's, an entry's, a live reply's and a day's, has a `cost` of 0, though PiG prices its answers at its catalog's rates.    - The service reads each session's entries newest first and stops at the first answer before `since`: a session's answers are written in the order of their times. It reads every session it keeps sums of, and every one whose `updatedAt` is on or after the oldest day a `since` may name: its transcript, not its `updatedAt`, says whether it has an answer since `since`, as a stop between an answer's write and the write of its session's time leaves the time behind.
   - It keeps the days' sums of each session it read, in memory, through the newest entry it read, and reads on from there, so each answer is read once while it runs. A `since` before the first day it kept of a session reads that session again from `since`. Each report drops the kept days before the oldest day a `since` may name, and the sessions left with none that were not updated since then. **Saved prompts** ([ADR-0051](../adr/0051-insert-the-owners-saved-prompts-into-the-composer-with-a-slash.md))

65. `GET /v1/prompts` lists the owner's saved prompts: the files of the `prompts` folder of the profile folder that end in `.md`, but those whose name starts with a dot, by name (the file's name without `.md`), at most 100 of them. It changes nothing, and has no event: the service reads the folder at each request, so a change shows at the next one.
   - The service reads the folder through the profile folder it pinned at start, as rule 21 reads a profile: `prompts` is a folder of its own, never a symbolic link, and each file a regular file with no other name, never read through a link nor waited on as a named pipe. No `prompts` folder lists none. A folder that cannot be read, or a profile folder no longer the one the service protects, lists none, and `problem` says why. A service that runs without profiles lists none, with no `problem`. A folder of more than 100 prompt files lists the first 100 by name, and `problem` says so.
   - A prompt's `name` is its file's name without `.md`: 1 to 64 lowercase letters, digits and `-`, starting with a letter or a digit. The file is at most 16,384 bytes of UTF-8. It may start with front matter between `---` lines: one YAML document, a map whose only keys are `description`, text of at most 300 characters, and `argument-hint`, text of at most 100, each read as written, none twice, with its white space made single spaces and no control character. Its `text` is the rest of the file without the white space around it: not empty, and with no control character but tabs and line breaks.
   - A valid prompt lists its `name`, `description`, `argumentHint` and `text`. A file that breaks a rule lists only its `name` and `problem`, and the others still list.
   - A client puts a prompt's text in its message composer, each `$ARGUMENTS` in it replaced by what followed the name; it never sends it on its own.

**Changes** ([ADR-0053](../adr/0053-show-a-sessions-changes-read-with-isolated-git-in-code.md))

66. `GET /v1/sessions/{id}/changes` answers what the session changed in the git checkout its folder (`cwd`) is in (`Changes`). It writes nothing, takes no `requestId` and sends no event.
   - A folder in no checkout, with no `.git` in it or a folder above it, answers `repository` false, and no other field but `sessionId` and an empty `files`. A folder whose checkout git cannot read, or whose reading git refuses at a later step (a partial clone that lacks what a diff needs), is `conflict`, with git's words.
   - Otherwise it names the checkout's `top`, its `branch` (absent when `HEAD` is detached) and `head` (absent before the first commit), the `base` the changes are counted against and its `baseRule`, and the `mergeBase` they are counted from:
     - `pull`: the base branch of the newest open pull request linked to the session's thread (rule 36), else of its newest; the session is the thread's specialist, its worker (rule 47), or a review of one of its pull requests (rule 46). It is `origin/<base>`, else the local branch, when the checkout has one.
     - `default`: else the checkout's default branch: the branch `origin/HEAD` names, else `origin/main`, `origin/master`, `main`, `master`.
     - `head`: else none, and `base` is absent: only what is not committed counts, from `HEAD`.
     - `mergeBase` is the merge base of that branch and `HEAD`; `HEAD` when the two share no commit, which counts as `head`; the empty tree of the repository's object format, SHA-1 or SHA-256, before the first commit, when the branch `HEAD` names has no ref yet; a `HEAD` that names a commit git cannot read is `conflict`. Only the exact names of the candidates count, not the refs below them.
   - `files` lists each file that differs between `mergeBase` and the folder, at most 300 (`proto.MaxChangedFiles`), and `more` counts the files left out:
     - the tracked ones, in git's order, each with its lines `added` and `removed`, `binary` when git counts none, a renamed one's `oldPath`, `committed` when a commit since `mergeBase` changed it and `uncommitted` when the folder changes it since `HEAD`, staged or not, by either end of each part's change, a rename's old path too;
     - then the files git does not track and does not ignore, `new` and `uncommitted`, but one at the path of a listed tracked change, as a file removed from the index and kept in the folder, which is that change. The lines of the first 30 of them are counted (`proto.MaxCountedNew`), listed or not, from the file's bytes, read below the checkout's top through no link, as git counts them against nothing: a link its target's lines, a binary file (a NUL in its first 8,000 bytes) none. The rest are `uncounted`, as is a file past 1 MiB and one gone or no longer a file when it is read. A repository inside the checkout, which git lists as its folder with a `/` at its end, and a path that is no UTF-8, which `path` spells with U+FFFD and no request can name, are `uncounted` and `noDiff`: the service shows no diff of them.
     - `added` and `removed` total the lines of every file counted, those left out included.
   - git runs in the sandbox (rule 14e), version 2.45 or later, else the read is `conflict`. Its options ignore replacement objects, run no hook, fsmonitor, pager, external diff, text conversion or attribute the checkout sets, take no optional lock, so no read writes the index, fetch nothing a partial clone lacks, name each path literally, and show a submodule by its commits alone. Before it reads a file of the checkout, and again once it read, the service checks what no option turns off: an `info/attributes` in the checkout's repository, or a system attributes file, is `conflict`, and its message says which. It names the checkout's top by its identity (its device, inode and birth time) as the read begins: a top that is another folder when a new file is read, or by the read's end, is `conflict`.
   - One read runs git for at most 30 seconds, and the service runs 4 reads at once: another waits for a place while its request lasts.
67. `GET /v1/sessions/{id}/changes/file?path=<path>` answers one file's unified diff from `mergeBase` to the folder (`FileDiff`), by rule 66's base, as rule 66 runs git. It writes nothing and takes no `requestId`.
   - `path` is the file's path as `Changes` lists it: 1 to 4,096 bytes of UTF-8 with no NUL, from the checkout's top, with no empty, `.` or `..` part; another is `bad_request`, before the session is looked at.
   - Only a listed change is read: a tracked file git's numstat names from `mergeBase`, its own change alone, whatever the folder holds as git runs (a renamed one's from its old path, across a folder's boundary too; what a folder that takes the name of one of its ends holds left out, never the end itself, a submodule included, nor the other end), or a file git does not track and does not ignore, whose diff against nothing the service writes from its bytes, read below the checkout's top through no link, as git writes one: mode 100755 for a file its owner may run, a link's target as its content, line by line, a path git quotes quoted as git quotes it. Any other path, one no longer a file when it is read, or a folder in no checkout, is `not_found`.
   - `diff` is at most 65,536 bytes (`proto.MaxFileDiff`) as the client decodes it, each byte that is no UTF-8 a U+FFFD of its own. A longer one ends after its last whole line that fits, and `cut` says so.

**Renaming a session** ([ADR-0058](../adr/0058-rename-a-private-agents-session-from-the-desktop-checked-in-code.md))

68. `POST /v1/sessions/{id}/title` renames a private agent's session (`RenameSession`), as the owner asks.
   - `title` is a string the body names: a body without one, or with `null`, is `bad_request`, and keeps no record. It is at most 200 bytes as sent (`proto.MaxTitle`), else `bad_request`. It is trimmed, and an empty one gives `Session <id>` (`proto.DefaultTitle`).
   - The service decides from the session's record and its profile as it reads it at the request (`team.CheckRename`). It refuses with `bad_request` and the reason, and changes nothing, a session:
     - started from no profile: the owner's own;
     - it started for the team's work: a thread's specialist, a worker (rule 47), a cross-review (rule 46), a consult (rule 52) or a gather's ask (rule 58), whatever its profile says now;
     - whose profile is gone or invalid now, and any session while the service runs without profiles;
     - whose profile is not `private` now;
     - of a `private` profile with the role `supervisor`.

     A profile it cannot read now is `internal`, and a profile folder that is no longer the one it protects is `conflict`. A private profile's standing session (rule 7c) may be renamed, whoever opened it, a schedule (rule 57) included, and keeps the new title.
   - The rename changes the title alone, in one transaction with the request's record. The session's id, `cwd`, model, route, worktree and branch (rule 6a), thread, pull requests and pins stay. Its `updatedAt` stays too, so it keeps its place in `GET /v1/sessions`, and search finds the new title at that time (rule 63). The service publishes the session (rule 16b), then answers 200 with it.
   - A retry with the same `requestId` answers the session as it is now, renames nothing again, and publishes the session again (rule 5). The id reused with another `title`, or for another session, is `conflict`. A refused or failed rename keeps no record.
   - Every `Session` the service sends (the list, the detail, its events and every answer that carries one) has `renamable` set when the rule takes the session, its profile read as that copy is read, and leaves it out otherwise, a profile it cannot read then included. A client offers a rename only on a session that has it.

**Sign-ins** ([ADR-0062](../adr/0062-sign-pocketd-in-to-github-copilot-from-the-desktop-with-a-device-flow-it-runs.md))

69. A client signs pocketd in to GitHub Copilot with GitHub's device flow, which pocketd runs: the owner enters a code at GitHub's device page, and pocketd keeps the sign-in. The client never sees or keeps a token.
   - **The providers.** `GET /v1/signins` lists the subscriptions pocketd signs in to (`signins.Providers`), in that order: `github-copilot`, `anthropic`, `openai-codex`. Each has its `state`: `signed_in` for a subscription's sign-in pocketd runs on, `expired` for one whose access token expired with no refresh token to renew it, `none` otherwise, an API key included (`signins.State`). pocketd refreshes a sign-in itself, and cannot tell a refresh token the provider revoked until it uses it: such a sign-in shows `signed_in`. `account` is the GitHub login, an enterprise managed user's included (`signins.Login`), pocketd kept when it signed in from a device flow, shown only while the credential it was kept with is the one stored (`signins.Account`): none for a sign-in made with `pocketd login`. `deviceFlow` is set for `github-copilot` alone: the others sign in on the service host, with `pocketd login`, and a start or sign-out of one is `bad_request`, which names that command. `flow` is the provider's newest device flow since pocketd started, running or ended. No answer and no event carries a token or the device code.
   - **A start.** `POST /v1/signins/{id}` (`StartSignIn`), `{id}` the provider's id, asks GitHub for a code, for Copilot's OAuth app with the `read:user` scope, as PiG's own sign-in does, and answers 201 with the flow. A provider has one flow at a time: a start while one waits answers that one, 200. pocketd takes GitHub's answer only field by field: a `user_code` of 1 to 32 printable characters, a `verification_uri` over HTTPS on `github.com`, an `expires_in` of 1 second to an hour, and an `interval` of at most 5 minutes, 5 seconds when GitHub names none. A start GitHub does not answer so is a flow `failed` at once, with why, answered 201 like any other.
   - **The flow.** A `SignInFlow` has its `id`, `provider`, `state`, `userCode`, `verificationUri`, `expiresIn` and `interval` in seconds, `startedAt`, `expiresAt` (`startedAt` plus `expiresIn`, by the service's clock), `endedAt` once it ended, `account` once approved, and `error` once denied, expired or failed. Its `state` is `waiting`, then one of `approved`, `denied`, `expired`, `canceled` and `failed`. pocketd polls GitHub after each `interval`, the first after one interval, never past `expiresAt`: `authorization_pending` waits on, `slow_down` widens the wait by 5 seconds, or to the interval GitHub names when longer, for every later poll, past the first wait's 5-minute bound too, `access_denied` ends it `denied`, `expired_token` or `expiresAt` ends it `expired`, and any other error ends it `failed`, in pocketd's words: GitHub's code when it is an OAuth error code (lowercase letters and underscores), never the text GitHub sent with it, which could echo the device code. A poll that does not reach GitHub, or gets a 5xx or a 429, is tried at the next interval; the third in a row ends the flow `failed`. A request that does not reach GitHub is said in pocketd's words, never in the text of the error, which could quote what GitHub sent.
   - **The approval.** A token ends the poll, in a 2xx answer with no error beside it alone; one in another answer fails the flow. pocketd reads the account's login from GitHub's API with it (none when GitHub names no valid login), exchanges it for Copilot's token as PiG does, and writes the sign-in through the engine's own credential store, the one the engine refreshes the tokens through, under the store's lock, in place of the one it held; then the flow is `approved`, with the `account`. `GET /v1/models` lists the Copilot models the account offers from that moment, with no restart (ADR-0022). A sign-in pocketd could not keep ends the flow `failed`, with why, which never holds the token. Unlike `pocketd login`, the sign-in enables no Copilot model whose policy is not set on the account: such a model lists, and its first call may be refused until the owner enables it on GitHub.
   - **A cancel.** `POST /v1/signins/flows/{id}/cancel` (`CancelSignIn`) ends a `waiting` flow `canceled`, and pocketd polls it no more; it answers 200 with the flow as it is then. An ended flow, and one whose approval pocketd is keeping, stay as they are: the latter ends `approved` or `failed`. `GET /v1/signins/flows/{id}` answers the flow as it is. A flow does not outlive pocketd: one a stop ended is no longer kept, and its id is `not_found`, as is the id of a provider's flow its next start replaced.
   - **A sign-out.** `DELETE /v1/signins/{id}` cancels the provider's waiting flow and takes the sign-in out of the engine's credential store, with no approved flow's keep between: one under way ends first, and the sign-out then takes what it kept. pocketd forgets the account, publishes the provider's sign-in and answers 200 with it, `none`. A sign-out with no sign-in changes nothing and answers the same; a credential that is no subscription's, as an API key a Pi-format file holds for the provider, stays. The Copilot models leave `GET /v1/models` at once. A session on a Copilot model keeps its model, and its next model call fails for want of a sign-in (`No API key for provider: github-copilot`), which ends its run as a provider's failure does; the next sign-in makes it work again.
   - **Events.** A `signin` event carries the provider's sign-in as `GET /v1/signins` lists it, after a flow starts or ends, and after a sign-out, in the order pocketd read them. One whose read of the store fails carries the state last published. A client fetches `GET /v1/models` and `GET /v1/profiles` again, from a `signin` event or a `GET /v1/signins` answer that brings the change first, when a provider's `state` changes, and when a flow was approved since, which may sign in another account with other models.
